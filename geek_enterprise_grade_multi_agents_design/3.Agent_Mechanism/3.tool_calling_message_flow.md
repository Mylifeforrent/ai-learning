# 原生 Tool Calling 消息机制深度剖析 —— 以 LangGraph 为例

> **本文是 `react_message_accumulation.md` 的姊妹篇**。上篇讲的是 CrewAI 的纯文本 ReAct 模式（用 `stop` 词截断 + 正则提取），本篇讲解的是当前主流的**原生 Tool Calling 模式**。

## 为什么用 LangGraph 作为示例框架？

| 候选框架 | 是否使用原生 Tool Calling？ | 说明 |
| :--- | :--- | :--- |
| **LangGraph** ✅ | **是，默认就是** | LangChain 团队最新推出的 Agent 架构，通过 `llm.bind_tools()` 直接将 Python 函数绑定为原生 Tool Calling Schema。是目前最主流、最具代表性的框架。 |
| CrewAI | 底层也在逐步切换 | CrewAI 最新版在检测到模型支持时，会在底层偷偷用 Tool Calling，但用户体验层面仍然展现 ReAct 文本格式。 |
| AutoGPT（早期） | 否 | AutoGPT 早期的 JSON 约束是靠 Prompt 硬写的，不是原生 Tool Calling。 |
| 纯 OpenAI SDK | 是 | 原生支持，但它是裸 API，没有 Agent 循环逻辑。LangGraph 就是在此基础上封装了状态机和循环。 |

**结论**：LangGraph 是展示原生 Tool Calling 在 Agent 框架中如何运作的最佳选择。

---

## 1. 四种消息角色（比 ReAct 多了一个 `tool`）

在原生 Tool Calling 模式中，消息列表出现了**第四种角色 `tool`**：

| Role | 写入者 | 内容 | 对比 ReAct 模式 |
| :--- | :--- | :--- | :--- |
| `system` | 开发者/框架 | 大模型的人设和规则 | ✅ 相同 |
| `user` | 用户 | 用户的原始提问 | ✅ 相同，**但不再需要冒充注入 Observation** |
| `assistant` | 大模型生成 | 大模型的回复，可能包含 `tool_calls` 结构体 | ⚡ 不再是纯文本！当需要调用工具时，content 为空，取而代之的是结构化的 `tool_calls` 数组 |
| **`tool`** 🆕 | 框架执行工具后写入 | 工具的真实返回结果 | 🆕 **ReAct 模式没有这个角色**，只能把工具结果冒充成 `user` |

> **核心升级**：大模型现在能明确分辨"人类说的话"(user) 和"工具返回的数据"(tool)，不再混淆。

## 2. 完整 API 日志模拟

**任务**：查询北京天气 + 查询紫外线指数，综合给出穿衣建议。  
**可用工具**：`get_weather(city)` 、`get_uv_index(city)`

---

### 🔄 第 1 轮 API 请求

框架发给 OpenAI API 的完整请求体：
```json
{
  "model": "gpt-4o",
  "messages": [
    {
      "role": "system",
      "content": "你是一个天气预报专家，请使用提供的工具来获取真实数据，再给用户专业建议。"
    },
    {
      "role": "user",
      "content": "帮我查一下北京今天天气和紫外线情况，给出穿衣建议。"
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询指定城市的天气",
        "parameters": {
          "type": "object",
          "properties": { "city": { "type": "string", "description": "城市名" } },
          "required": ["city"]
        }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "get_uv_index",
        "description": "查询指定城市的紫外线指数",
        "parameters": {
          "type": "object",
          "properties": { "city": { "type": "string", "description": "城市名" } },
          "required": ["city"]
        }
      }
    }
  ]
}
```

> 📌 注意看：**工具定义不在 system prompt 里！** 它作为独立的 `tools` 字段传入，与消息列表完全分离。这是与 ReAct/AutoGPT 把工具描述硬塞进提示词的根本区别。  
> 📌 也没有 `stop` 词！不再需要这个 Hack。

**大模型返回（原始 API 响应）**：
```json
{
  "choices": [{
    "finish_reason": "tool_calls",
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [
        {
          "id": "call_abc123",
          "type": "function",
          "function": {
            "name": "get_weather",
            "arguments": "{\"city\": \"Beijing\"}"
          }
        },
        {
          "id": "call_def456",
          "type": "function",
          "function": {
            "name": "get_uv_index",
            "arguments": "{\"city\": \"Beijing\"}"
          }
        }
      ]
    }
  }]
}
```

> 📌 **关键差异点**：
> - `finish_reason` 不是 `"stop"`，而是 `"tool_calls"` —— 这是模型发出的原生信号："我需要调工具，别急着让我回答"。
> - `content` 是 `null` —— 模型**没有**输出任何自然语言文字！没有 `Thought:` 也没有 `Action:`。
> - `tool_calls` 是一个**结构化数组**，框架直接用 SDK 对象访问，完全无需正则解析。
> - 支持**并行调用多个工具**（这里同时请求了天气和紫外线两个工具（不过也取决于模型的能力以及框架是不是支持同时调用），ReAct 模式每次只能调一个！，比如ReAct模式来2轮：第一轮：我需要查询上海的天气。第二轮：我还需要查询北京的天气）。

**框架代码在后台的操作**：

```python
import json

# SDK 直接返回结构化对象，无需正则！
for tool_call in assistant_message.tool_calls:
    func_name = tool_call.function.name            # "get_weather" 或 "get_uv_index"
    func_args = json.loads(tool_call.function.arguments)  # {"city": "Beijing"}
    
    # 本地执行真实函数
    if func_name == "get_weather":
        result = get_weather(func_args["city"])     # "阴转小雨，8-14度，北风3级"
    elif func_name == "get_uv_index":
        result = get_uv_index(func_args["city"])    # "紫外线指数2，强度较弱"
    
    # 以 tool 角色追加到消息列表（必须带上 tool_call_id 用于配对）
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": result
    })
```

### 🔄 第 2 轮 API 请求

框架组装的 `messages` 列表（累积追加）：
```json
{
  "model": "gpt-4o",
  "messages": [
    {
      "role": "system",
      "content": "你是一个天气预报专家..."
    },
    {
      "role": "user",
      "content": "帮我查一下北京今天天气和紫外线情况，给出穿衣建议。"
    },
    {
      "role": "assistant",
      "content": null,
      "tool_calls": [
        { "id": "call_abc123", "type": "function", "function": { "name": "get_weather", "arguments": "{\"city\": \"Beijing\"}" } },
        { "id": "call_def456", "type": "function", "function": { "name": "get_uv_index", "arguments": "{\"city\": \"Beijing\"}" } }
      ]
    },
    {
      "role": "tool",
      "tool_call_id": "call_abc123",
      "content": "北京今天阴转小雨，气温8-14度，北风3级"
    },
    {
      "role": "tool",
      "tool_call_id": "call_def456",
      "content": "紫外线指数2，强度较弱，无需特别防晒"
    }
  ],
  "tools": [ "（与第1轮相同的工具定义，省略）" ]
}
```

> 📌 **此时有 5 条消息**：
> 1. `system` — 不变
> 2. `user` — 原始问题，不变
> 3. `assistant`（含 `tool_calls`）— 第 1 轮模型的工具请求，**content 为 null**
> 4. `tool` — get_weather 的真实结果，通过 `tool_call_id` 与请求配对
> 5. `tool` — get_uv_index 的真实结果，同样配对
>
> 对比 ReAct 模式：ReAct 无法并行调工具，同样的场景需要 4 轮请求（调天气→拿结果→调紫外线→拿结果），而 Tool Calling 只需要 2 轮！

**大模型返回（最终回答）**：

```json
{
  "choices": [{
    "finish_reason": "stop",
    "message": {
      "role": "assistant",
      "content": "北京今天阴转小雨，气温8-14度，北风3级。紫外线指数较弱。\n\n穿衣建议：\n1. 建议穿薄款羽绒服或厚外套，注意防风保暖\n2. 外出请携带雨伞\n3. 紫外线较弱，无需涂抹防晒霜"
    }
  }]
}
```

> 📌 `finish_reason` 现在是 `"stop"` → 表示模型已给出最终自然语言回答，循环结束。

## 4. LangGraph 框架代码完整示例

```python
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI
from langchain_core.messages import SystemMessage, HumanMessage
from langchain_core.tools import tool
from typing import Annotated, TypedDict
import operator

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 第一步：定义工具（普通 Python 函数 + @tool 装饰器）
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气"""
    # 真实场景会发起 HTTP 请求
    return f"{city}今天阴转小雨，气温8-14度，北风3级"

@tool
def get_uv_index(city: str) -> str:
    """查询指定城市的紫外线指数"""
    return f"{city}紫外线指数2，强度较弱"

tools = [get_weather, get_uv_index]

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 第二步：初始化 LLM 并绑定工具
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
llm = ChatOpenAI(model="gpt-4o")
# ⭐ 关键一行：bind_tools() 会将 Python 函数签名转换为 OpenAI Tool Calling 的 JSON Schema
# 发送请求时，它会自动填入 API 的 tools 参数（而不是塞进 system prompt）
llm_with_tools = llm.bind_tools(tools)

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 第三步：定义图的状态（消息列表会自动累积）
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
class AgentState(TypedDict):
    # operator.add 的含义：每个节点返回的新消息会自动追加到列表尾部
    # 这就是"消息累积"的代码体现！不需要手动管理
    messages: Annotated[list, operator.add]

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 第四步：定义图节点
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

def agent_node(state: AgentState):
    """大脑节点：调用 LLM 进行推理（或请求调工具）"""
    messages = state["messages"]
    # 在消息列表头部加入 System Prompt
    if not isinstance(messages[0], SystemMessage):
        messages = [SystemMessage(content="你是天气预报专家，请用工具获取真实数据再回答。")] + messages
    
    # 调用大模型 → 返回的 response 可能是普通文本，也可能包含 tool_calls
    response = llm_with_tools.invoke(messages)
    return {"messages": [response]}  # 自动追加到 state["messages"]

# ToolNode 是 LangGraph 预置的工具执行节点
# 它会自动：提取 tool_calls → 执行对应 Python 函数 → 以 tool 角色返回结果
tool_node = ToolNode(tools)

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 第五步：构建图结构（状态机）
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

builder = StateGraph(AgentState)
builder.add_node("agent", agent_node)    # 大脑节点
builder.add_node("tools", tool_node)      # 工具执行节点

# 定义流转路径
builder.add_edge(START, "agent")          # 入口 → 先给大脑思考

# tools_condition 是官方的路由函数：
#   - 如果 agent 返回了 tool_calls → 路由到 "tools" 节点
#   - 如果 agent 返回了普通文本 → 路由到 END（任务完成）
builder.add_conditional_edges("agent", tools_condition, {"tools": "tools", END: END})

# 工具执行完后 → 回到大脑，让它消化结果继续推理（可能再调工具，也可能给出最终回答）
builder.add_edge("tools", "agent")

graph = builder.compile()

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 第六步：运行！
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
initial_state = {"messages": [HumanMessage(content="帮我查一下北京天气和紫外线，给出穿衣建议。")]}

for event in graph.stream(initial_state, stream_mode="values"):
    message = event["messages"][-1]
    message.pretty_print()
    # 第1次输出：AIMessage(tool_calls=[...])       ← 模型请求调工具
    # 第2次输出：ToolMessage("阴转小雨8-14度")     ← 工具真实结果
    # 第3次输出：ToolMessage("紫外线指数2")         ← 工具真实结果
    # 第4次输出：AIMessage("穿厚外套，带伞...")     ← 最终回答
```

## 5. LangGraph 内部的消息累积流转

用上面的代码为例，`state["messages"]` 的变化过程如下：

```
初始：
  messages = [HumanMessage("帮我查北京天气和紫外线...")]

经过 agent_node 第1次执行后：
  messages = [
    HumanMessage("帮我查北京天气和紫外线..."),
    AIMessage(content=None, tool_calls=[{get_weather}, {get_uv_index}])  ← 自动追加
  ]

经过 tool_node 执行后 (ToolNode 自动执行并返回结果)：
  messages = [
    HumanMessage("帮我查北京天气和紫外线..."),
    AIMessage(content=None, tool_calls=[...]),
    ToolMessage("阴转小雨，8-14度", tool_call_id="call_abc123"),         ← 自动追加
    ToolMessage("紫外线指数2", tool_call_id="call_def456"),              ← 自动追加
  ]

经过 agent_node 第2次执行后：
  messages = [
    HumanMessage("帮我查北京天气和紫外线..."),
    AIMessage(content=None, tool_calls=[...]),
    ToolMessage("阴转小雨，8-14度", tool_call_id="call_abc123"),
    ToolMessage("紫外线指数2", tool_call_id="call_def456"),
    AIMessage("穿厚外套，带伞，无需防晒...")                             ← 最终回答！
  ]
  → tools_condition 检测到没有 tool_calls → 路由到 END → 循环结束
```

> 📌 整个消息累积过程完全由 LangGraph 的 `Annotated[list, operator.add]` 自动管理，开发者无需手动拼接。

## 6. 两种模式的终极对比

| 对比维度 | ReAct 纯文本模式 (CrewAI) | 原生 Tool Calling (LangGraph) |
| :--- | :--- | :--- |
| **工具定义放在哪？** | 硬写在 system prompt 文本中 | 独立的 `tools` API 参数 |
| **模型如何表达"我要调工具"？** | 输出纯文本 `Action: xxx` | 返回结构化 `tool_calls` 对象 |
| **如何截停模型？** | `stop: ["Observation:"]` 截断 | `finish_reason: "tool_calls"` 原生信号 |
| **工具结果用什么角色？** | `user`（冒充用户注入） | `tool`（专属角色 + `tool_call_id` 配对） |
| **能否并行调多个工具？** | ❌ 不行，每次只能一个 | ✅ 可以，一次返回多个 `tool_calls` |
| **解析方式** | 正则匹配，极易出错 | SDK 直接返回 Python 对象 |
| **同样场景需几轮 API？** | 查天气+紫外线 = 至少 **4 轮** | 查天气+紫外线 = 最少 **2 轮** |
| **Token 消耗** | 每轮都需携带完整 Thought/Action 文本 | assistant 的 content=null 节省文本量 |
| **适用条件** | 任何模型（含不支持 Tool Calling 的小模型） | 需要模型原生支持 Tool Calling |

---

## 7. 总结

原生 Tool Calling 相对于 ReAct 纯文本模式，本质上是同一个思想的**工业化升级**：

> **ReAct 模式**：让大模型**扮演**能用工具的角色（靠提示词催眠） → 再用 stop 词和正则来"钳制"和"提取"它的输出。  
> **Tool Calling**：让大模型**真正理解**工具调用这一概念（靠底层微调训练） → API 层面返回结构化对象，无需任何 Hack。

LangGraph 就是当前最主流的 Agent 框架，它通过 `bind_tools()` + `ToolNode` + `tools_condition` 三个组件，完整地封装了 Tool Calling 的消息累积循环，让开发者只需定义"工具函数"和"图结构"，其余的消息管理完全自动化。
