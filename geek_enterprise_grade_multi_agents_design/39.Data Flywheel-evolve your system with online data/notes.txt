<p>上节课，我们给 AI 系统装上了一整套线上监控——六层指标、告警策略、从延迟到用户满意度的全链路感知。你现在能在用户之前发现问题，知道哪里在冒烟。</p>
<p>但知道哪里冒烟，和让系统不再冒烟，是两回事。</p>
<p>监控是<strong>被动防御</strong>，让你及时响应；而这节课要讲的，是<strong>主动进化</strong>——如何把每一次用户交互、每一个失败案例、每一个"它又给出了错误答案"的瞬间，都变成让系统下一次更聪明的养料。这套机制，叫做<strong>数据飞轮</strong>。</p>
<p><img src="https://static001.geekbang.org/resource/image/13/ee/1365046bc6bea10db4ec04ea7781eaee.png?wh=2816x1522" alt="图片"></p>
<p>没有飞轮的系统，<strong>只能停在线上那一刻的状态</strong>。用户的问题在变，场景在变，而系统原地踏步，质量只会相对下降。更糟糕的是——AI 应用的开发门槛正在快速降低，任何人都能快速搭一个原型上线。真正的护城河不是技术有多先进，而是<strong>你有没有飞轮</strong>——运行得越久，积累的真实失败案例越多，Prompt 越精准，知识库越完善，用户体验越好，用户越多……这个循环一旦转起来，就很难被追上。</p>
<p><img src="https://static001.geekbang.org/resource/image/3d/fe/3d8cb48506fffbae5f2534a5e40f35fe.png?wh=2810x1506" alt="图片"></p>
<p>飞轮让企业 AI 系统有了<strong>持续进化</strong>的能力。不是因为某个算法有多神奇，而是因为时间在里面——时间越久，数据越多，护城河越深。后来者即使技术完全相同，它没有你的历史数据，就无法复制你的效果。</p>
<h2>一、认知原点：数据飞轮的本质到底是什么？</h2>
<p><strong>数据飞轮的本质，就是一个把用户行为变成系统改进的自强化循环。</strong></p><!-- [[[read_end]]] -->
<p><img src="https://static001.geekbang.org/resource/image/88/b5/88068a7eb22cde4e4b6e9905fcf367b5.png?wh=2996x1536" alt="图片"></p>
<p>换成软件工程的话说：你在生产环境里有一个持续运行的系统，用户的每一次操作都在产生信号——有些是主动的反馈（点赞 / 踩），大多数是被动的行为（用户有没有真的采纳 AI 的建议，有没有立即改写重问，有没有在关键步骤中途放弃）。飞轮要做的，是把这些信号系统性地采集→筛选→分析→修复→验证→上线，然后再产生新信号，进入下一轮循环。</p>
<pre><code class="language-plain"><table class="hljs-ln"><tbody><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="1"><div class="hljs-ln-n" data-line-number="1"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="1">线上用户交互</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="2"><div class="hljs-ln-n" data-line-number="2"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="2">  → [Step 1] 采集信号（显式反馈 + 隐式行为）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="3"><div class="hljs-ln-n" data-line-number="3"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="3">  → [Step 2] 筛选有价值 case，进入 Bad Case 分析管道</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="4"><div class="hljs-ln-n" data-line-number="4"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="4">  → [Step 3] 构建 / 扩充 Eval 数据集</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="5"><div class="hljs-ln-n" data-line-number="5"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="5">  → [Step 4] 定向修复（Prompt / 工具描述 / RAG / Harness / 微调）→ Eval 验证 → CI/CD</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="6"><div class="hljs-ln-n" data-line-number="6"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="6">  → [Step 5] 灰度上线</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="7"><div class="hljs-ln-n" data-line-number="7"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="7">  → 采集新信号（回到 Step 1，进入下一圈）</td></tr></tbody></table></code></pre>
<p>为什么叫"飞轮"而不是"管道"？因为管道是线性的，跑完一遍就停；飞轮是循环的，而且越转越快——每一圈结束，你手里的数据更丰富，分析更精准，改进更有效，用户体验更好，下一圈的信号质量就更高。</p>
<p>这和传统软件改进的区别很根本：传统软件靠工程师主观判断"哪里需要改"；AI 产品靠用户行为数据<strong>驱动</strong>"哪里需要改、改了之后有没有变好"。<strong>不是工程师在管理 AI，而是用户在喂养 AI。</strong></p>
<p>三个真实案例，让你看到飞轮跑起来的效果：</p>
<p><strong>案例 A：电信运营商 AI 客服（对话类）</strong></p>
<p>某北美电信运营商聊天机器人上线时自动化率只有 <strong>34%</strong>，大量简单问题被迫升级到人工。飞轮的核心信号是"升级率"——当机器人无法解决问题时，系统记录这次失败的完整上下文，定期对这批 session 做人工分析（<strong>开放编码</strong>），识别高频失败类型，补充 FAQ、优化对话流程。9 个月后：自动化率从 34% 升至 <strong>67%</strong>，每年节省约 <strong>45 万美元</strong>。</p>
<p><strong>案例 B：Glean 企业内部搜索（知识管理类）</strong></p>
<p>Glean 是一款企业级 AI 搜索和知识管理平台，帮助员工快速查找内部文档和信息。上线初期，员工反馈"查不到想要的文档"——信息分散在 Drive、Slack、Jira 等多个系统，搜索返回的结果往往不对。</p>
<p>飞轮机制：</p>
<ul>
<li>
<p>核心信号（显式 + 隐式）：</p>
<ul>
<li>
<p>显式：用户主动标记"未找到答案"、对搜索结果点赞 / 踩</p>
</li>
<li>
<p>隐式：同一问题的重复搜索次数、搜索会话时长、最终是否找到答案（通过后续行为推断）</p>
</li>
</ul>
</li>
<li>
<p>迭代方式：内容团队每周分析高频未解决问题 → 人工补充 FAQ 或完善文档 → 重新索引 → 验证新员工上手时间是否缩短</p>
</li>
</ul>
<p>效果（明确数据）：</p>
<ul>
<li>
<p>新员工入职时间缩短 <strong>36 小时</strong></p>
</li>
<li>
<p>每名员工每年节省 <strong>110 小时</strong></p>
</li>
<li>
<p>IT/HR 支持请求减少 <strong>20%</strong></p>
</li>
<li>
<p>2 年内采用率达到 <strong>93%</strong></p>
</li>
</ul>
<p><strong>案例 C：Claude Code（代码辅助类）</strong></p>
<p>前段时间 Claude Code 源码公开，让我们第一次能看到 Anthropic 的工程设计内部——整个框架里全是遥测埋点，几乎每一个关键路径都有监控节点。Anthropic 正是基于这些埋点数据，进行各种各样的定向修复。这是 Claude Code 成为一套好用工程框架的重要原因：不只是技术出色，而是有飞轮在持续驱动改进。<strong>其中最值得学习的信号设计，我们后面会专门拆解</strong>——用情绪信号捕获用户挫败时刻。</p>
<p>三个完全不同的场景，同样的结论：<strong>飞轮转得快慢，取决于信号收得多不多、准不准。</strong> 那么，信号怎么设计？</p>
<h2>二、为什么需要飞轮：没有它，系统只能停在线上那一刻</h2>
<p>在讲信号设计之前，先回答一个问题：没有飞轮，会怎样？</p>
<p>你的 AI 系统上线了。第一天，它表现不错；第一周，用户开始抱怨"有时候不太准"；第一个月，同样的问题反复出现，团队忙于救火；三个月后，竞品上线了一个功能相似的产品，质量却更好——因为他们有三个月的飞轮数据，而你没有。</p>
<p><strong>没有飞轮的系统，只能停在线上那一刻的状态。</strong> 时间越久，世界在变，用户在变，问题在变，而系统原地踏步，质量相对只会下降。飞轮要解决的核心问题是：<strong>如何让系统不停在上线那一天，而是随着每一次运行不断变好。</strong></p>

<p>这段话在 X.com 上获得了超过一万次浏览——因为它写出了太多团队的真实处境。Agent 上线了，技术指标全绿，用户在悄悄流失。你甚至不知道问题出在哪里，因为没有信号采集体系，没有失败案例分析，没有持续迭代的机制。</p>
<p>飞轮的价值，不仅在于"改进"，更在于<strong>护城河</strong>——时间换壁垒。后来者即使技术完全相同，它没有你一年的生产数据，就无法复制你的效果。这就是企业级 AI 系统的核心竞争力：不是你上线那天有多强，而是你能多快地把用户行为变成系统改进。</p>

<p>其中<strong>礼貌偏差</strong>最值得单独说一说。面对 AI，很多人依然有社交压力——你问用户"这个回答怎么样"，他内心可能已经在默默翻白眼，嘴上却说"还行吧，还好的"，然后礼貌地给你点了个赞。越是"还过得去"的场景，这种偏差越严重。这是人类的本能，不是个别现象——所以依赖显式信号的系统，最终都会向"被接受而非真正有用"的方向漂移。</p>
<p><strong>设计共识</strong>：减少摩擦（按钮嵌入消息气泡）、负面后追问（分类标签转化率是空文本框 10 倍）、时机决定响应率（对话结束立即触发 CSAT 是邮件方式的 3 倍）。</p>

<p>一个值得专门拿出来讲的工程决策：为什么用<strong>正则表达式</strong>而不是<strong>LLM</strong>来检测情绪？<br>
Boris Cherny（Claude Code 工程负责人）的原话是：“computationally free at global scale”。用 LLM 检测每条消息的情绪，在全球规模下成本不可接受——几百万用户、每天数千万条消息，按 token 计费的 LLM 调用会把成本打爆。正则表达式足够简单、快、便宜，在这个场景下比 LLM 更适合，不是偷懒，是成熟的工程判断。</p>
<p><strong>隐式信号设计永远要考虑工程成本</strong>——不是越精细越好，是在信息量和实现成本之间找到最合适的平衡点。</p>
<p>还有一条更底层的直觉值得记住：<strong>找 bad case 不需要高召回率。</strong> 同样一个问题，有人骂出来，有人忍着没骂——你只要找到那个骂的用户，拿他这一条 case 去迭代就够了。那些浮出来的 bad case，往往你都看不完。先用简单方式能找着就行，找着了再迭代，不要为了"找完整"而在信号采集上过度投入。</p>

<h3>（二）一个具体例子：RAG 知识库查不到文档</h3>
<p>场景：企业内部知识库 AI，用户频繁投诉"查文档老是查不到"。</p>
<p><strong>Step 1 错误分析</strong></p>
<p>从过去一周的 session 里，提取 Rephrase Rate &gt; 60% 的 session（用户立即改写重问 = 检索失败的强信号）。</p>
<p>Open Coding：看 50 个这类 session，不要急着分类，先写自由文本笔记。发现大量查询是内部项目代号（“X2-Alpha 报错怎么处理”）、内部术语（“SKU 合并流程的 SOP”）。</p>
<p>Axial Coding 归类：</p>
<ul>
<li>
<p>内部术语查询失败：<strong>47%</strong></p>
</li>
<li>
<p>跨文档综合问题：<strong>32%</strong></p>
</li>
<li>
<p>文档过时问题：<strong>21%</strong></p>
</li>
</ul>
<p><strong>Step 2 根因诊断</strong></p>
<p>内部术语查询失败 → 向量模型在公网数据上训练，不懂内部代号 → <strong>BM25 关键词检索覆盖不到这类查询</strong></p>
<p>这不是生成问题（把正确上下文给模型，它能正确回答）→ <strong>纯粹的检索问题</strong></p>
<p><strong>Step 3 修复</strong></p>
<ul>
<li>
<p>增加 BM25 + 向量混合检索（覆盖精确关键词匹配）</p>
</li>
<li>
<p>建立内部术语词表，加入查询扩展</p>
</li>
</ul>
<p><strong>Step 4 验证</strong></p>
<ul>
<li>
<p>黄金集：50 条历史"内部术语"查询 → Recall@5 从 <strong>31% → 78%</strong></p>
</li>
<li>
<p>LLM-Judge 对整体回答质量打分：平均 <strong>3.2/5 → 4.1/5</strong></p>
</li>
</ul>
<p><strong>Step 5 上线</strong></p>
<p>Shadow mode 跑一周，确认无回归。全量上线后：Rephrase Rate 从 <strong>62% 降至 28%</strong>。</p>
<p>这就是飞轮的一个完整循环：一个行为信号（Rephrase Rate 异常高）→ 驱动出根因（检索覆盖缺口）→ 精准修复（混合检索）→ 数据验证（Recall + LLM-Judge）→ 线上验证（Rephrase Rate 回落）→ 进入下一轮。</p>

</li>
</ol>
<p>关键洞察：<strong>模型是原料，Harness 是产品</strong>。工程护城河在执行层精密设计，不在底层模型参数。</p>

<h2>五、避坑指南：反模式与最佳实践</h2>
<p>基于前面五节的内容，这里提炼<strong>4 个最严重的反模式</strong>（🚫 不要踩的坑）和<strong>4 条最关键的最佳实践</strong>（💡 一定要做的事）。它们各自独立，没有对应关系，都是真实团队的踩坑经验。</p>
<h3>🚫 反模式（4 条）</h3>
<p><strong>反模式 1：只部署点赞 / 踩，把最懒的信号当核心数据</strong></p>
<p><strong>现象</strong>：上线时加了 👍/👎 按钮，就认为"反馈机制有了"，不再投入隐式信号采集。</p>
<p><strong>致命后果</strong>：点赞 / 踩覆盖率 &lt; 5%，而且极易被 Goodhart’s Law 攻击——如果你只追踪满意度打分，Agent 会学会给出让用户开心而不是让用户正确的答案（Sycophancy）。单维信号必然被奖励黑客行为破坏。GitHub Copilot 的隐式信号（Tab 键接受率）覆盖率 100%，而显式评分覆盖率不到 5%，这就是差距。</p>
<p><strong>反模式 2：把"模型变蠢"直接归因为模型问题，跳过根因诊断</strong></p>
<p><strong>现象</strong>：用户投诉"AI 变笨了"，团队第一反应是"要不要换个模型"或"要不要微调"。</p>
<p><strong>致命后果</strong>：80% 的"模型变蠢"投诉实际是 context pollution——上下文窗口被垃圾历史记录、格式错误的工具输出或错误的 RAG 文档污染，而非模型本身的问题。直接跳到"换模型"会浪费资源且问题不解决。Claude Code 的 postmortem 显示，六周的"质量退化"来自三个独立的基础设施 Bug，没有一个跟模型有关。</p>
<p><strong>反模式 3：用合成数据构建微调集，上线后在真实分布上失败</strong></p>
<p><strong>现象</strong>：团队 week 2 就决定微调，基于对失败案例的"假设"构建了 1000 条合成训练数据，SFT 后在合成测试集上 SOTA。</p>
<p><strong>致命后果</strong>：真实用户行为总是和假设不同。合成集覆盖的是你能想象到的边缘场景，而真实失败发生在你根本没想到的地方。结果是：微调后模型在合成测试集上表现极好，在生产中失败的问题依然失败。用合成数据构建的微调集几乎必然失败。</p>
<p><strong>反模式 4：飞轮太慢——收集了数据但没有闭环更新机制</strong></p>
<p><strong>现象</strong>：团队建立了日志采集、用户反馈收集，但数据在数据库里沉睡。没有触发分析的机制、没有负责人、没有更新 Prompt/RAG/Eval 的 SOP。</p>
<p><strong>致命后果</strong>：只收不用，数据仓库不是飞轮。真实案例：团队积累了 6 个月生产数据，但从未用它更新过任何 Eval 用例。飞轮根本没有转起来。时间越久，数据越多，护城河反而越浅——因为你没有把它转化为改进。</p>
<h3>💡 最佳实践（4 条）</h3>
<p><strong>最佳实践 1：用"AI 建议 + 用户验证"的 UX 范式构建天然标注工厂</strong></p>
<p><strong>落地心法</strong>：把产品交互本身设计成数据采集管道——AI 主动给出建议，用户接受 / 修改 / 拒绝。接受 = 正标签；修改后接受 = 负 + 正对（pairwise，适合训练偏好模型）；拒绝 = 负标签。这套模式的数据采集转化率，比"请给我们打分"高 <strong>10 倍</strong>，而且是自然发生的，不需要用户任何额外操作。GitHub Copilot 的飞轮核心就是 Tab 键接受率，Midjourney 的核心就是图片保存 / 下载行为。</p>
<p><strong>最佳实践 2：优先挖掘隐式信号，把行为数据变成飞轮燃料</strong></p>
<p><strong>落地心法</strong>：用户行为比用户评分更诚实。对于代码类产品追踪 Tab 键接受率；对于内容类产品追踪复制 / 分享 / 下载行为；对于任务类产品追踪下游业务动作是否发生（订单完成、工单关闭）。用工具调用序列分析识别"技术上正确但路径错误"的静默失败（如：wrong tool called 3 steps earlier）。显式信号是"黄金标签"但覆盖率 &lt; 5%，隐式信号是"行为数据"覆盖率 100%，两者都要，缺一不可。</p>
<p><strong>最佳实践 3：遵循"先 Harness 层，后模型层"的修复决策顺序</strong></p>
<p><strong>落地心法</strong>：80% 的"模型变蠢"实际是 Harness 问题（Context Poisoning、循环参数、信息流层级）。修复优先级：(1) <strong>Prompt/ 工具描述</strong>（最快，0.5 人日）；(2) <strong>RAG/Skill 边界</strong>（周级）；(3) <strong>Harness 架构 / 上下文管理</strong>（1-3 人日）；(4) <strong>Eval 标准迭代</strong>（0.5 人日 / 月）；(5) <strong>微调</strong>（最后手段，需 1000+ 真实样本）。<strong>模型是原料，Harness 是产品</strong>——工程护城河在执行层精密设计，不在底层模型参数。</p>
<p><strong>最佳实践 4：把专家"品味"显式化，编码进系统提示和 Eval 标准</strong></p>
<p><strong>落地心法</strong>：“Taste is invisible until you try to write it down”。系统性地访谈领域内最优秀的分析师 / 客服 / 运营，让他们描述具体决策过程（“为什么这个答案好 / 不好”），把这些隐性判断标准提炼为 Prompt 中的显式规则和 Eval 的评分锚点。这个过程本身就是飞轮的一部分：隐性知识显式化 → 可复制 → 可测试 → 可改进。飞轮不仅改进模型，还改进团队对"好"的理解。</p>
<h2>课程总结</h2>
<ul>
<li>
<p>我们定义了<strong>数据飞轮</strong>的本质：一个把用户行为信号变成系统改进的自强化循环，越转越快，越转越深；</p>
</li>
<li>
<p>我们认识到<strong>没有飞轮的系统只能停在线上那一刻</strong>：时间越久，世界在变，用户在变，系统原地踏步，质量只会相对下降。飞轮让企业有了<strong>时间换壁垒</strong>的能力；</p>
</li>
<li>
<p>我们建立了<strong>完整的信号采集体系</strong>：显式信号是"黄金标签"（但覆盖率 &lt; 5%，且有四种偏差），隐式信号是"行为数据"（覆盖率 100%），两者都要，缺一不可；</p>
</li>
<li>
<p>我们跑通了<strong>从信号到修复的完整迭代流程</strong>：开放编码 → 轴心编码 → 根因诊断 → Prompt/RAG/Harness/Skill/Eval/ 上下文 / 微调（完整阶梯）→ Eval 验证 → 灰度上线；</p>
</li>
<li>
<p>我们理解了<strong>飞轮为什么是护城河</strong>：后来者即使技术相同，没有历史数据就无法复制。关键不是上线那天多强，而是能多快把用户行为变成系统改进。</p>
</li>
</ul>
