<h2>四、核心架构：HookRegistry 的两套机制</h2>
<p><code>HookRegistry</code> 是那根"零侵入"的骨干。Agent 代码对它毫无感知——它拦截 CrewAI 的回调，翻译成统一的事件体系，再交给各个 handler 处理。</p>

<p>还有一个容易忽略的细节：<code>HookContext</code> 是 <code>frozen=True</code> 的 dataclass，<code>tool_input</code> 和 <code>metadata</code> 转为 <code>MappingProxyType</code>（只读字典代理）。Handler 只能读数据，不能修改——防止一个 handler 篡改输入导致后续 handler 看到脏数据。</p>

<p><img src="https://static001.geekbang.org/resource/image/32/34/3277018da1030f73bf637318b4ddbe34.png?wh=1506x778" alt="图片"><br>
这个顺序是需要被设计的。下面是 <code>BEFORE_TOOL_CALL</code> 触发时的完整执行链：</p>
<pre><code class="language-plain"><table class="hljs-ln"><tbody><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="1"><div class="hljs-ln-n" data-line-number="1"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="1">BEFORE_TOOL_CALL（dispatch_gate）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="2"><div class="hljs-ln-n" data-line-number="2"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="2">  1. structured_log.before_tool_handler    ← 观测层（hooks 段）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="3"><div class="hljs-ln-n" data-line-number="3"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="3">  2. langfuse_trace.before_tool_handler    ← 观测层（hooks 段）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="4"><div class="hljs-ln-n" data-line-number="4"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="4">  3. sandbox_guard.before_tool_handler     ← 安全层（strategies 段，fail_closed）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="5"><div class="hljs-ln-n" data-line-number="5"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="5">  4. permission_gate.before_tool_handler   ← 访问控制（strategies 段，fail_closed）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="6"><div class="hljs-ln-n" data-line-number="6"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="6">  5. cost_guard.before_tool_handler        ← 预算检查（strategies 段）</td></tr></tbody></table></code></pre>
<p>以及 <code>AFTER_TURN</code>（每轮结算）：</p>
<pre><code class="language-plain"><table class="hljs-ln"><tbody><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="1"><div class="hljs-ln-n" data-line-number="1"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="1">AFTER_TURN（dispatch_gate）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="2"><div class="hljs-ln-n" data-line-number="2"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="2">  1. structured_log.after_turn_handler     ← 观测</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="3"><div class="hljs-ln-n" data-line-number="3"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="3">  2. langfuse_trace.after_turn_handler     ← 观测</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="4"><div class="hljs-ln-n" data-line-number="4"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="4">  3. cost_guard.after_turn_handler         ← 算账（必须在 loop_detector 前）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="5"><div class="hljs-ln-n" data-line-number="5"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="5">  4. loop_detector.after_turn_handler      ← 循环检测（可能 deny）</td></tr></tbody></table></code></pre>
<p>整个顺序应该是：<strong>首先观测→然后安全→最后成本</strong>。为什么？<br>
因为你要保证观测的记录全都被先记下来。一旦后面被拦掉、被 deny 掉、抛出异常以后，如果还没有观测，你会恰恰记录不到最关键的信息。所以一定是先观测，观测之后再做安全防护——拦截沙箱的东西、拦截权限的东西。然后最后再做成本相关的检查，防止成本计算因为前面 deny 了而没有执行，影响后面的运行。</p>
<p>这个顺序有三条关键约束，每条都有具体后果。</p>
<hr>
<h3>约束一：观测段必须整体先于策略段</h3>
<p><strong>问题：</strong> 观测 handler 和策略 handler 都注册在 <code>BEFORE_TOOL_CALL</code>。<code>dispatch_gate</code> 遇到 <code>GuardrailDeny</code> 立即中止迭代——如果策略先执行并拒绝，后面的 handler 全部跳过。</p>
<p><strong>不解决的后果：</strong> 攻击者发来路径穿越，SandboxGuard 拦截，但 Langfuse 没机会记录。被攻击的日志反而是最需要有记录的——结果 Langfuse 里什么都看不到。</p>
<p><strong>怎么解决的：</strong> <code>HookLoader</code> 硬编码 <code>_load_hooks_section()</code> 先于 <code>_load_strategies_section()</code> 执行，所有事件的观测 handler 都注册在策略 handler 之前。这不是约定，是代码强制。</p>
<pre><code class="language-python hljs"><table class="hljs-ln"><tbody><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="1"><div class="hljs-ln-n" data-line-number="1"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="1"><span class="hljs-comment"># xiaopaw/hook_framework/loader.py</span></td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="2"><div class="hljs-ln-n" data-line-number="2"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="2"><span class="hljs-keyword">def</span> <span class="hljs-title function_">load_from_directory</span>(<span class="hljs-params">self, hooks_dir: Path, ...</span>):</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="3"><div class="hljs-ln-n" data-line-number="3"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="3">    self._load_hooks_section(config, hooks_dir, layer_name, fail_closed_names)    <span class="hljs-comment"># ← 先执行</span></td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="4"><div class="hljs-ln-n" data-line-number="4"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="4">    self._load_strategies_section(config, hooks_dir, layer_name, fail_closed_names)  <span class="hljs-comment"># ← 后执行</span></td></tr></tbody></table></code></pre>
<p>即使 SandboxGuard 在步骤 3 触发 deny，步骤 1、2 已经执行完毕，Langfuse 里有这次调用的记录，并且 <code>after_tool_handler</code> 还会额外标记 <code>guardrail_deny: True</code>，给 Langfuse 加上被拦截的标记。</p>
<hr>
<h3>约束二：audit_logger 必须在 strategies 段中排第一</h3>
<p><strong>问题：</strong> <code>sandbox_guard</code> 和 <code>permission_gate</code> 声明了 <code>deps: {audit: audit_logger}</code>——它们需要共享同一个 <code>SecurityAuditLogger</code> 实例来写审计日志。<code>HookLoader</code> 按声明顺序实例化，如果 <code>audit_logger</code> 还没被实例化就去查 deps，返回 <code>None</code>。</p>
<p><strong>不解决的后果：</strong> <code>SandboxGuard.__init__(audit=None)</code> 被调用，运行时调用 <code>self.audit.log(...)</code> 时 <code>AttributeError</code>。而 <code>sandbox_guard</code> 是 <code>fail_closed=True</code>——安全组件自己崩了，等同于拒绝所有请求。系统完全瘫痪，每一条消息都返回"安全策略拦截"。</p>
<p>陷阱在于：<code>HookLoader</code> 在 deps 找不到时只打 WARNING，不崩溃（fail-open 设计，开发友好）。实际的爆炸发生在 <code>SandboxGuard</code> 内部第一次调用 <code>audit</code> 时，而且是 fail_closed 的爆炸——把所有请求都拒掉，最难排查。</p>
<p><strong>怎么解决的：</strong> <code>hooks.yaml</code> 的 strategies 段中，<code>audit_logger</code> 声明在第一位。</p>
<pre><code class="language-yaml hljs"><table class="hljs-ln"><tbody><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="1"><div class="hljs-ln-n" data-line-number="1"></div></td><td <h3>约束三：cost_guard 必须先于 loop_detector（AFTER_TURN）</h3>
<p><strong>问题：</strong> <code>AFTER_TURN</code> 触发时，<code>cost_guard</code> 负责算账（把这轮的 token 成本累积进去），<code>loop_detector</code> 负责检测是否循环（可能抛 <code>GuardrailDeny</code>）。<code>dispatch_gate</code> 遇到 deny 立即中止，cost_guard 被跳过。</p>
<p><strong>不解决的后果：</strong> 循环场景是高消耗场景——Agent 在重复调用工具，偏偏是最需要准确计费的情况。但因为 loop_detector 先触发了 deny，cost_guard 永远没机会运行。时间长了，<code>cost_guard</code> 的预算计算严重偏低，"1 美元预算"可能实际已经花了 3 美元。</p>
<p><strong>怎么解决的：</strong> <code>hooks.yaml</code> 的 strategies 段中，<code>cost_guard</code> 声明在 <code>loop_detector</code> 前面。AFTER_TURN 的执行顺序是先算账再检测，即使 loop_detector 触发 deny，cost_guard 的账已经记下来了。</p>

<h2>六、Trace 树：从事件到完整树形结构</h2>
<p>刚才大家看到了 Langfuse 里那棵清晰的 trace 树。现在最有意思的一个问题来了：<strong>这么多零散的 hook 节点上面的东西，是怎么穿成这棵树的？</strong></p>
<p><img src="https://static001.geekbang.org/resource/image/bc/17/bc246dbbea8b1a6327eafd7f6676a117.png?wh=1723x670" alt="图片"><br>
这里有五个关键机制。</p>
<h3>机制一：多轮对话如何留在同一棵树</h3>
<p><strong>问题：</strong> 一次对话有多轮消息。Langfuse 里怎么让 Turn 1 和 Turn 2 归属同一条 trace，而不是变成两棵独立的树？</p>
<p><strong>怎么解决的：</strong> <code>trace_id = session_id</code>，不使用随机 UUID。<code>trace-create</code> 在 Langfuse 里是 upsert 操作——相同 ID 的第二次调用是更新，不是新建。</p>

<p>每轮有自己的 root span（<code>session-{sid}</code>），但都挂在同一个 trace 下。用对话 ID 作为 trace ID，这样就能保证所有对话都在一棵树里面。</p>
<hr>

<hr>
<h3>机制三：Span 栈保证嵌套工具调用的父子关系</h3>
<p><strong>问题：</strong> 工具可以嵌套调用（主 skill → sub-crew → sub-skill）。某一时刻可能有多个 span 同时处于 open 状态。新开的 span 应该挂在哪个父节点下？</p>
<p><strong>怎么解决的：</strong> <code>_span_stack_var</code> 是一个不可变元组模拟的栈（方便 ContextVar 传播）：</p>
<ul>
<li>
<p><code>BEFORE_TOOL_CALL</code>：把新 span 的 <code>(span_id, tool_name, turn_number, tool_input)</code> 压栈</p>
</li>
<li>
<p><code>AFTER_TOOL_CALL</code>：从栈里弹出对应的 span，关闭它</p>
</li>
<li>
<p>新的 span 或 generation 的 parent = 栈顶 span ID</p>
</li>
</ul>
<p>嵌套调用时，后压入的先弹出（LIFO），天然匹配嵌套结构。</p>

<h3>机制四：Generation 先写后更新</h3>
<p><strong>问题：</strong> LLM 调用在 <code>BEFORE_LLM</code> 时知道开始了，但什么时候结束？系统里没有 <code>AFTER_LLM</code> 事件。</p>
<p><strong>怎么解决的：</strong> Generation 的生命周期跨越两个事件点：</p>
<ol>
<li>
<p><strong>BEFORE_LLM</strong>：<code>generation-create</code>（有 start_time 和 input prompt，无 output）</p>
</li>
<li>
<p>Generation 在以下时机被关闭：</p>
<ol>
<li>
<p><strong>下一次 BEFORE_LLM</strong>：Agent 拿到工具结果后再次调用 LLM，此时关闭上一个 generation，并从 <code>prompt_messages</code> 里找出工具结果，补全对应 tool span 的 output</p>
</li>
<li>
<p><strong>AFTER_TURN</strong>：本轮最后一次 LLM 调用，在 <code>after_turn_handler</code> 里关闭</p>
</li>
</ol>
</li>
</ol>

<h3>机制五：强制 flush 保证用户可见性</h3>
<p><strong>问题：</strong> Langfuse SDK 把事件放在内存 buffer 里，攒够再批量发送。用户收到 XiaoPaw 的回复后立刻打开 Langfuse，buffer 还没发出去，trace 一片空白。</p>
<p><strong>怎么解决的：</strong> <code>after_turn_handler</code> 末尾强制调用 <code>_flush_batch()</code>，以 50 个事件为一批发送到 Langfuse API：</p>
<pre><code class="language-plain"><table class="hljs-ln"><tbody><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="1"><div class="hljs-ln-n" data-line-number="1"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="1">AFTER_TOOL_CALL（数据入 buffer）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="2"><div class="hljs-ln-n" data-line-number="2"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="2">→ AFTER_TURN（关闭最后的 gen/span）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="3"><div class="hljs-ln-n" data-line-number="3"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="3">→ _flush_batch()（把 buffer 全部推送到 Langfuse）</td></tr><tr><td class="hljs-ln-line hljs-ln-numbers" data-line-number="4"><div class="hljs-ln-n" data-line-number="4"></div></td><td class="hljs-ln-line hljs-ln-code" data-line-number="4">→ sender.send(reply)（用户收到回复）</td></tr></tbody></table></code></pre>
<p>flush 发生在 <code>send(reply)</code> 之前。用户拿到回复的同时，Langfuse 里已经有完整数据。Langfuse 本身有缓存机制，为了让你能实时看到它有一个强制 flush 的机制——这样你执行完了就能在 Langfuse 里看到整个数据。</p>
