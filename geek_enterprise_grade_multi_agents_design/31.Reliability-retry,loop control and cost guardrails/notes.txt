<p>但这里有个问题：<strong>你不可能一直盯着 Dashboard。</strong> Agent 凌晨三点触发了一个任务，你不在；周末跑了一批数据处理，你不看。就算你看了，看见 Agent 第 47 轮还在重复搜索——然后呢？你能做的只是手动停掉它，但损失已经发生了。</p>
<p>观测解决的是看见的问题。但真正让 Agent 变得可靠的，不是看见，而是<strong>自动干预</strong>。利用上节课搭好的 Hook 骨架，在关键节点上挂载策略——不是记录日志，而是在问题发生的那一刻就拦截。这节课我们做的就是这件事：在 30 课的 Hook 骨架上插入三个可靠性策略，让系统自己保护自己。</p>

<h2>一、三个痛点，三个策略</h2>
<blockquote>
<p>💡 课程说明：本节代码已同步至 GitHub，地址：<a href="https://github.com/kid0317/crewai_mas_demo/blob/main/m5l31/" rel="noopener nofollow">https://github.com/kid0317/crewai_mas_demo/blob/main/m5l31/</a></p>
</blockquote>
<p>在给出方案之前，先看看 Agent 在生产环境里最常遇到的三个可靠性问题。它们分别指向我们今天要实现的三个策略。</p>
<p><img src="https://static001.geekbang.org/resource/image/cb/a0/cbe3c2ccdffaa367b39faf6f43e8c9a0.png?wh=1588x699" alt="图片"></p>
<p>需要提前说明的是：<strong>课程中的三个痛点是通用痛点</strong>——所有 Agent 系统都会遇到。但你在自己的业务里，一定要发现自己的痛点。比如金融场景，Agent 在工具请求中发出了用户身份证号，你可能就要立刻拦住它；代码场景，Agent 提交的代码没过单测，你也要在 Hook 层拦截。这些业务专属的护栏策略，同样可以用我们今天搭的框架来实现——写一个策略类，挂到 Hook 上就行。</p><!-- [[[read_end]]] -->
<p><strong>痛点一：长任务被单步失败拖垮。</strong> 你的 Agent 执行一个三小时的复杂任务——调用了上百次模型，做了几十次工具调用。到最后一步，某个 API 返回了 500 错误。整个任务失败，前面三小时全白跑。问题是，这个 500 错误可能只是服务端的瞬态抖动——等 2 秒再试一次就好了。但你的 Agent 不会重试，它直接报告失败。<strong>一个长任务会成百次调用模型，任意一次的偶发失败都会拖垮整体成功率。</strong> 这指向我们的第一个策略：<strong>重试</strong>。</p>
<p><strong>痛点二：Agent 陷入死胡同无限循环。</strong> Agent 在推理过程中遇到了一个它解决不了的问题，但它不知道自己解决不了——它反复用同样的参数调同一个工具，每次得到同样的结果，然后再试一次。它可能循环 200 次才被 <code>max_iter</code> 硬性截断。相同参数重复 200 次花了 $63、两个 Agent 互聊六小时花了 $200——这些都是真实发生的事故。<strong>Agent 没有"记住自己已经试过"的机制，同样的输入大概率产生同样的输出。</strong> 这指向我们的第二个策略：<strong>循环检测</strong>。</p>
<p><strong>痛点三：Agent 真的在干活，但方式太贵。</strong> Agent 没有循环，确实在有效推进任务。但它选择的方式有问题——用了最贵的模型、加载了过多的上下文、做了不必要的深度搜索。它干了一夜，第二天早上你发现账单 $300。它做完了事情，但成本完全不可接受。<strong>Agent 的成本不可预测性是结构性的——同一个任务可能 3 步也可能 17 步。</strong> 这指向我们的第三个策略：<strong>成本围栏</strong>。</p>
<p>三个问题，三个策略。下面逐个展开。</p>
<hr>
<h2>二、重试：什么时候该重试，什么时候不该</h2>
<p>重试本身在工程上很简单——等一下再试一次。<strong>Agent 场景下，难的不是"怎么重试"，而是"该不该重试"。</strong> 错误的重试比不重试更贵。</p>

<p>这个判断才是重试策略的核心。如果你不区分错误类型，一律重试，结果就是：400 错误重试了 3 次，每次都失败，还往上下文里塞了 3K 垃圾 token。</p>
<h3>Agent 场景为什么最多 2-3 次</h3>
<p>不只是因为第 4 次大概率也不行——更重要的是，<strong>每次失败的错误信息都会留在上下文里</strong>。一次失败的报错信息通常 1-3K token，三次重试就多了将近 10K 垃圾 token。上下文越脏，后续推理质量越差。重试有隐性成本：不只是多花一次调用的钱，还污染了后续所有步骤的上下文。</p>
<h3>RetryTracker：观测重试效果</h3>
<p>重试本身不是在 Hook 层做的——重试是调度层的事情，框架自己会处理。Hook 能帮你做的是<strong>重试的追踪和观测</strong>：哪些工具在反复失败？重试成功率多少？该不该调整重试策略？</p>
<p>我们的 <code>RetryTracker</code> 是纯观测的——它不决定"要不要重试"（这是框架的事），它记录"重试了几次、成功了没有"：</p>

<h2>三、循环检测：Agent 最贵的 Bug 是无限循环</h2>
<p><img src="https://static001.geekbang.org/resource/image/7e/c4/7e94ae98ca239599dd28ebc2e817e8c4.png?wh=1515x753" alt="图片"></p>
<p>为什么 Agent 特别容易循环？因为 <strong>LLM 没有"记住自己已经试过"的机制</strong>。同样的输入大概率产生同样的输出，于是同样的失败反复发生。你的 Agent 用完全一样的参数重试了 200 多次，$63。<code>max_iter=200</code> 确实能救它，但你已经浪费了 197 次的钱。</p>

<p>你可能会问：这和 CrewAI 自带的 <code>max_iter</code> 有什么区别？</p>
<p><code>max_iter</code><strong>是限速器，哈希去重是方向检测。</strong> <code>max_iter=200</code>，但 200 次里可能只有 3 次是重复——其余 197 次是有效推进。哈希去重在第 3 次重复就发现了"你在兜圈子"。两者不矛盾：<strong>哈希去重是精准检测，</strong><code>max_iter</code><strong>是最后防线，双保险。</strong></p>
<h3>为什么需要两个独立的哈希列表</h3>
<p>你可能注意到了 <code>_tool_hashes</code> 和 <code>_turn_hashes</code> 两个列表。这跟 CrewAI 的两种执行路径有关：</p>
<ul>
<li>
<p><strong>ReAct 模式</strong>：每次工具调用后触发 <code>step_callback</code>（对应 AFTER_TURN）</p>
</li>
<li>
<p><strong>原生 function calling 模式</strong>：只在最终回答时触发 <code>step_callback</code>——中间的工具调用不触发</p>
</li>
</ul>
<p>如果只在 AFTER_TURN 里检测循环，原生 FC 路径下工具连续循环调用 10 次你都发现不了。所以循环检测必须<strong>双路径覆盖</strong>：<code>after_turn_handler</code> 检测推理循环，<code>after_tool_handler</code> 检测工具调用循环。两条线各自独立计数，互不干扰。</p>
<hr>
<h2>四、成本围栏：在 Agent Loop 里实时算账</h2>
<p>Agent 的成本不可预测性是结构性的——1 个用户动作触发 3 到 30+ 个 LLM 调用，团队预估和实际差 3-5 倍不是估不准，是 Agent 路径本身非确定性。</p>
<p>你在 System Prompt 里写"请控制成本不超过 $10"。Agent 非常配合："好的我会注意控制成本的"。然后花了 $50。因为<strong>它根本不知道每次调用花了多少钱</strong>——成本控制必须在 Hook 层用代码实现，不能靠 Agent 自觉。</p>

<h2>五、代码实战：从策略到 Hook 的工程落地</h2>
<blockquote>
<p>🧠 <strong>回忆一下</strong>：上节课我们讲了 <code>dispatch()</code> 是 fire-and-forget——handler 异常被吞掉，不影响执行。但可靠性策略需要的是<strong>阻断能力</strong>——检测到循环就停、超预算就拒绝。这就是这节要解决的核心工程问题。</p>
</blockquote>

<h2>六、避坑指南：最佳实践与反模式</h2>
<h3>🚫 严重破坏可靠性的"反模式"</h3>
<p><strong>1. 靠 Prompt 控制成本：Agent 说"好的"然后超支 5 倍</strong></p>
<p><strong>现象</strong>：System Prompt 里写"请控制成本不超过 $10"，Agent 回复"好的我会注意控制成本"。实际花费 $50。<strong>致命后果</strong>：Agent 没有成本感知能力，它不知道每次调用花了多少钱。Prompt 层面的成本控制就像跟员工说"注意节约"但不给预算表——态度很好，执行为零。<strong>成本控制必须在 Hook 层用代码实现，不能靠 Agent 自觉。</strong></p>
<p><strong>2. 只设 max_iter 不做状态去重：200 次无效循环才停下来</strong></p>
<p><strong>现象</strong>：设了 <code>max_iter=200</code> 作为安全网。Agent 从第 3 次开始就在重复，但一直到第 200 次才被停下来。<strong>致命后果</strong>：197 次无效推理，每次都在烧 token。<code>max_iter</code> 是最后防线，不是检测机制——它不关心"内容是不是重复的"，只关心"次数够了没有"。<strong>状态哈希去重在第 3 次就能发现循环，省下 197 次的成本。</strong></p>
<p><strong>3. 所有错误都重试：不可恢复错误白白浪费 token</strong></p>
<p><strong>现象</strong>：不区分错误类型，400/401/403 也重试。每次都失败，还往上下文里塞 1-3K 垃圾 token。<strong>致命后果</strong>：三次无效重试 = ~10K 上下文污染，后续推理质量急剧下降。<strong>区分可重试（429/5xx 瞬态）vs 不可重试（4xx 永久），只对瞬态错误重试。</strong></p>
<p><strong>4. 用请求数限流而不用 token：成本差几百倍</strong></p>
<p><strong>现象</strong>：不管是循环次数控制还是成本围栏，都用"请求次数"而非 token 计量。设了"最多 50 次请求"就觉得安全了。<strong>致命后果</strong>：Agent 的每次请求 token 量天差地别——一次简单的工具调用和一次带几万上下文的推理，成本可以差几百倍。用请求数做限流和成本控制没有任何实际意义。<strong>所有限流和成本围栏都应该换算到 token——包括 Agent 的整体限流，因为服务器能扛多少也取决于 token 总量，而不是请求数。</strong></p>
<h3>💡 稳健落地的"最佳实践"</h3>
<p><strong>1. 先记录再判断：成本累加必须在循环检测之前</strong></p>
<p><strong>落地心法</strong>：AFTER_TURN 事件上，cost_guard.accumulate 的注册顺序必须在 loop_detector 之前。<code>dispatch_gate</code> 在第一个 GuardrailDeny 处就停止后续 handler。如果循环检测先执行并 deny，成本累加被跳过——已发生的成本必须先记录，然后才能做拦截判断。</p>
<p><strong>2. 度量驱动调参：跑一周数据再定阈值</strong></p>
<p><strong>落地心法</strong>：不要拍脑袋定阈值。先用宽松阈值（重试 3 次、循环 5 次、大预算）跑一周，收集 <code>retry_success_rate</code>、<code>loop_detections</code>、<code>budget_utilization</code> 数据。数据告诉你：第 3 次重试成功率 2%（改成 2 次）、2 次重复就足够判定循环（阈值从 5 降到 2）。</p>
<p><strong>3. 启用重试前确保工具幂等性</strong></p>
<p><strong>落地心法</strong>：有副作用的操作（支付、发消息、写数据库）在启用重试前必须实现幂等键。金融工具超时后重试 = 双重扣款。非幂等工具不启用自动重试，或加幂等键后再启用。更进一步说，<strong>只要是给模型用的工具，都建议做成幂等的</strong>——模型的不确定性会导致它不知道多少次调用同一个工具，幂等是你唯一的安全网。</p>
<p><strong>4. token 估算用粗估就够，精确计费走 Langfuse</strong></p>
<p><strong>落地心法</strong>：护栏场景不需要精确到每个 token 的计算——那需要调用 tokenizer API，成本太高。生产上的做法是粗估：中文按字符数 × 1.5，英文按字符数 × 1.2，大差不差。我们代码里用 <code>max(1, len(text) * 2 // 3)</code> 做统一估算，精度足够做围栏决策——差 10-20% 不影响"$0.50 的预算是否用完了"这种判断。<strong>最终的精确计费，异步在 Langfuse 里完成</strong>——观测层做精确，护栏层做快速。</p>

<h2>课程总结</h2>
<ul>
<li>
<p>我们从三个生产痛点出发——<strong>单步失败拖垮长任务、无限循环烧钱、成本失控</strong>——引出了三个对应的可靠性策略。</p>
</li>
<li>
<p>我们理解了 Agent 场景下重试的核心不是"怎么重试"而是<strong>“什么时候该重试”</strong>——区分可重试的瞬态错误和不可重试的永久错误，最多 2-3 次，因为每次重试都有上下文污染的隐性成本。</p>
</li>
<li>
<p>我们实现了<strong>状态哈希去重的循环检测</strong>——双路径覆盖 ReAct 和原生 FC，配合 <code>max_iter</code> 做双保险。哈希去重第 3 次就发现循环，<code>max_iter</code> 是最后防线。</p>
</li>
<li>
<p>我们实现了<strong>实时成本围栏</strong>——代码层硬停止，不靠 Agent 自觉。粗估 token 做围栏决策，精确计费走 Langfuse。</p>
</li>
<li>
<p>我们在代码实战中理解了 <code>dispatch_gate</code>（报警器→保险丝）和 <code>pending_deny</code> 模式（绕过框架异常吞噬），并用 <code>hooks.yaml</code> 的 <code>strategies</code> 段实现了声明式加载——新增策略只需写一个 <code>.py</code> 文件加一段 YAML 声明。</p>
</li>
</ul>
<p>今天讲的三个策略是通用护栏——重试、循环、成本，所有 Agent 系统都会遇到。但你的业务一定有<strong>自己独特的护栏需求</strong>：金融场景要拦截用户身份证号等敏感信息泄露，编程场景要保证单测必须通过才能提交，客服场景要检测情绪升级……这些策略同样用 Hook 框架落地——写一个策略类，在 <code>hooks.yaml</code> 里声明，完成。</p>
<p>现在你的 Agent 不会无限循环，不会烧钱。但这一切有个前提：<strong>Agent 是善意的，用户输入是正常的。</strong> 如果有人在 Prompt 里注入恶意指令？如果 Agent 尝试执行危险操作？可靠性保证你的 Agent 不会"蠢死"，但不能保证它不会"被骗"。<strong>下一节课，我们加安全——沙箱、权限网关与身份认证</strong>，让系统不只是可靠，而且安全。我们下节课见！</p>
