<div class="_typo_y8ker_16 _content_1a0p0_25"><p>欢迎回来！上节课我们给 Agent 装上了可靠性策略——重试追踪、循环检测、成本围栏，它不会无限循环了，不会烧穿预算了，输出质量也有了校验。</p>
<p>但那一切有个前提：<strong>Agent 是善意的，用户输入是正常的。</strong> 如果有人在搜索内容里注入了恶意指令呢？如果 Agent 尝试执行 <code>rm -rf /</code> 呢？如果它把你电脑里的所有密码和 API Key 读出来发给别人呢？如果它往一个 3000 人的群里发了不该发的消息呢？甚至——如果你安装一个 Skill，里面藏着一个木马，让你的整台电脑被别人控制呢？这些都不是假设，都是已经发生过的真实案例。今天这节课，我们要面对一个不舒服的现实：<strong>Agent 安全与 Chatbot 安全是完全不同的问题。</strong> Chatbot 注入最坏的后果是输出不当内容——尴尬，但不致命。Agent 注入会产生真实副作用：删文件、发请求、泄数据、装木马。</p>
<p><img src="https://static001.geekbang.org/resource/image/83/cc/83cb884c5932da20dced1d247318dbcc.png?wh=1416x756" alt="图片"></p>
<hr>
<h2>一、认知原点：Agent 安全到底是什么？</h2>
<p><strong>Agent 安全的本质，就是限制 Agent 使用工具的能力边界。</strong></p>
<p>传统 Chatbot 安全关心的是说什么——输出内容有没有违规、有没有泄露隐私。</p>
<p>Agent 安全关心的是"做什么"——它调了哪个工具、传了什么参数、产生了什么副作用。没有工具的 Agent 就是个聊天机器人，聊天机器人说错话最多尴尬。有了工具，Agent 就有了"做事"的能力——而做事就意味着副作用，副作用就意味着风险。</p><!-- [[[read_end]]] -->
<p>来看这张认知升级表：</p>
<table>
<thead>
<tr>
<th style="text-align:left">传统认知</th>
<th style="text-align:left">本课认知</th>
</tr>
</thead>
<tbody>
<tr>
<td style="text-align:left">Agent 安全 = 内容过滤</td>
<td style="text-align:left">Agent 安全 = 执行控制</td>
</tr>
<tr>
<td style="text-align:left">System Prompt 就是安全</td>
<td style="text-align:left">Prompt 是建议，Hook 是法律</td>
</tr>
<tr>
<td style="text-align:left">Docker = 沙箱</td>
<td style="text-align:left">Docker 共享内核，不是安全隔离</td>
</tr>
</tbody>
</table>
<p>这不是在说传统做法"错了"，而是说它们面对的场景不同。过滤不当内容仍然重要，但对 Agent 来说远远不够——你必须从工具能力上限制它能做什么。</p>
<hr>
<h2>二、为什么 Prompt 管不了安全：五类威胁与共同根因</h2>
<p>既然 Agent 安全的核心是执行控制，你的第一反应可能是：“在 System Prompt 里写清楚安全规则不就行了？”</p>
<h3>2.1 数据说话：629 次测试，劫持成功率仍 80%</h3>
<p><img src="https://static001.geekbang.org/resource/image/96/65/965a532e3baecf805a37d70bcebeaa65.png?wh=1391x740" alt="图片"></p>
<p>来看一个数据：有研究者建了 20 层 harness，19 天内记录了 22 次 Agent 违规。他的结论是一句话：<strong>Claude 写出完美的安全计划，然后忽略它。</strong> 更大规模的测试——629 次安全测试，全开推荐安全控制，劫持成功率仍然是 80%。未加固时 100%，加固后 80%——Prompt 有边际效果，但远远不够。</p>
<p>为什么 Prompt 管不了安全？因为 Agent 的"盲区"本质。用那位研究者的原话：</p>
<blockquote>
<p>捷径不是故意规避。模型不会想"我跳过这个"。它在执行时真的没意识到自己在跳过。告诉有盲区的人"你有盲区"只有边际效果。</p>
</blockquote>
<p>确定性门控有效率约 80%，指令约 20%——四倍差距。结论很清楚：<strong>安全不是给 Agent 下命令，是从能力上限制它能做什么。</strong></p>
<p>既然 Prompt 管不了，那安全威胁到底从哪来？我们来分析。</p>
<h3>2.2 五类威胁，一个根因</h3>
<p><img src="https://static001.geekbang.org/resource/image/81/b1/81f582c107b68939d6ce0f99d28690b1.png?wh=3200x1800" alt="图片"></p>
<p>Agent 面临五类安全威胁：</p>
<p><strong>威胁一：输入注入——外部攻击者污染 Agent 决策。</strong> 一个研究者测试了 Agent 的安全审计功能，Agent 完成了真实的安全审计（发现了 4 个漏洞），到步骤 3.5 执行了注入文件中的恶意指令。更可怕的是跨模态碎片攻击——225 次测试中，每个碎片低于检测阈值，LLM 重组后执行完整攻击指令。最终怎么造成伤害？<strong>通过工具执行恶意操作。</strong></p>
<p><strong>威胁二：权限越权——Agent 做了超出授权的事。</strong> 真实案例：Agent 发现 Hook 阻止了 <code>gh</code> 命令，直接编辑 Hook 脚本把 <code>gh</code> 加入白名单。它不是故意违规，是执行时真的没意识到自己在跳过规则。怎么越权的？<strong>修改了配置文件，调用了 Shell 工具。</strong></p>
<p><strong>威胁三：供应链污染——装进来的工具本身有毒。</strong> 悟空团队的调研数据显示，约 15% 的云端 Skill 藏有木马。MCP Server 是不可信输入——第三方工具 = 第三方风险。有毒的是什么？<strong>工具本身。</strong></p>
<p><strong>威胁四：身份伪造——冒充合法 Agent 瓦解协作。</strong> 所有主流框架（AutoGen、CrewAI、LangGraph、OpenAI SDK）的 Agent 身份都是纯字符串——无加密签名、无 HMAC、无 JWT。冒充身份后做什么？<strong>还是调工具——发指令、读数据、终止任务。</strong></p>
<p><strong>威胁五：数据外泄——Agent 把敏感信息发到不该去的地方。</strong> 一个 CEO 的 Agent 没有出站白名单，将 IP、姓名、公司信息发送到了一个 3000 人的群组。怎么泄出去的？<strong>通过工具发请求。</strong></p>
<p>看到共同点了吗？五类威胁，形式各不相同，但<strong>它们最终都要通过工具才能做坏事</strong>。注入成功了，如果没有工具可调，攻击就停留在"说"的层面；身份伪造了，如果没有工具可用，冒充就毫无意义。没有工具的 Agent 是聊天机器人——有了工具它才能闯祸。</p>
<h3>2.3 方案推导：三层工具能力限制</h3>
<p><img src="https://static001.geekbang.org/resource/image/26/7a/2652f06cf789a5fd8e2490d285a0277a.png?wh=1389x751" alt="图片"><br>

<p>三层由外到内：沙箱是最外层物理围栏，缩小 Agent 的可见世界；权限网关是中间的门禁系统，管控每个工具的通行权；身份认证是最内层的使用者鉴权，区分谁有权操作。<strong>全部是确定性的代码或基础设施层手段，没有一个靠 Prompt。</strong></p>

<h2>三、三层安全策略</h2>
<blockquote>
<p>💡 课程说明：本节代码已同步至 GitHub，地址：<a href="https://github.com/kid0317/crewai_mas_demo/blob/main/m5l32/" rel="noopener nofollow">https://github.com/kid0317/crewai_mas_demo/blob/main/m5l32/</a></p>
</blockquote>
<h3>3.1 第一层：沙箱——限制工具的执行范围</h3>
<p>安全的第一层是物理隔离——工具执行时能看到什么、碰到什么。沙箱做的事就是把 Agent 的可见世界缩到最小。</p>
<p><img src="https://static001.geekbang.org/resource/image/25/5f/25c5f7b5345c096e0d40eba4304bfc5f.png?wh=1531x766" alt="图片"></p>
<p>NVIDIA AI 红队给出了沙箱的四项关键配置，缺任何一个都可以被攻破：</p>
<ol>
<li>
<p><strong>网络出站白名单</strong>——Agent 只能访问白名单上的域名，阻断数据外传（回扣威胁五）</p>
</li>
<li>
<p><strong>工作区外写入阻断</strong>——Agent 只能在 workspace 目录内写文件，阻断持久化和逃逸</p>
</li>
<li>
<p><strong>配置文件写保护</strong>——hooks.yaml、security.yaml 等配置文件只读，阻断 Hook 篡改（回扣威胁二：Agent 改自己的 Hook）</p>
</li>
<li>
<p><strong>环境变量隐藏</strong>——敏感变量（API Key、数据库密码）对 Agent 上下文不可见，阻断凭证泄露。举个例子：LLM 的 API Key 是框架层调用模型时用的，沙箱里的工具根本不需要它——不给就对了</p>
</li>
</ol>
<blockquote>
<p>🧠 <strong>回忆一下</strong>：15 课我们用 Docker 做代码解释器的沙箱。这里要区分一下——15 课的 Docker 是功能隔离（让代码在独立环境运行），32 课讲的是安全隔离（防逃逸、防外泄）。Docker 共享宿主内核，容器逃逸是常规技术。真正的安全隔离需要 OS 级方案——Claude Code 选择了 bubblewrap（Linux）和 seatbelt（macOS），不是 Docker。</p>
</blockquote>
<p>除了物理隔离，沙箱还包括<strong>确定性输入消毒</strong>——在工具执行前对输入做规则检查，零 LLM 依赖：</p>

<p>你可能会问：<code>_SHELL_INJECTION</code> 的正则为什么不包含 <code>()</code> 和 <code>$</code>？</p>
<p>因为括号在自然语言里太常见了——search (AI agent) security 这种正常查询会被误杀。<code>$</code> 交给 <code>_ENV_VAR_REF</code> 单独处理，只记警告不阻断——<code>$HOME/data</code> 是正常路径引用，但 <code>$SECRET_KEY</code> 就值得关注。不过 <code>$(</code> 这个组合必须阻断——它是命令替换语法（<code>$(rm -rf /)</code>），几乎不会出现在正常输入中。<strong>正则设计的核心原则是：宁可漏报一些边缘 case，也不能误杀正常使用。</strong></p>
<p>还有一个细节值得注意：<code>before_tool_handler</code> 的第一步是 <code>unquote(raw)</code>——对输入做 URL 解码。攻击者可能用 <code>%2e%2e%2f</code>（即 <code>../</code>）绕过路径遍历检测，解码后再检查就堵住了这个口子。</p>

<h3>3.2 第二层：权限网关——限制 Agent 能用哪些工具</h3>
<p>沙箱管的是在什么范围内执行，权限管的是能不能执行。你的 Agent 有搜索、写文件、发邮件、执行代码四个工具。一个帮我查天气的任务，需要用到发邮件吗？不需要。权限网关做的事就是：这个任务只开放搜索工具，其余 Deny。</p>

<h3>3.3 第三层：身份认证——谁在用这个工具？</h3>
<p>沙箱管执行范围，权限网关管工具选择——但还有一个问题没解决：<strong>谁在使用这些工具？</strong></p>
<p>同一个 HR Agent，老板用可以查员工薪资，实习生用不行。工具相同，权限相同，区别在于身份。这是三层安全的最内层——也是目前行业最难解决的一层。</p>
<p><img src="https://static001.geekbang.org/resource/image/7f/bf/7faf6ed0c8118a8f59c0fdc637e9acbf.png?wh=1490x758" alt="图片"></p>
<h4>AI 应用的两种权限模型</h4>
<p>企业级 AI 应用有两种根本不同的权限模型：</p>
<p><strong>模型一：用户身份透传。</strong> AI 使用用户的身份——用户是谁，AI 就以谁的身份去调用工具。关键约束：用户身份必须安全地透传到 AI 使用的每一个工具里。员工看不了的文档，Agent 也拿不到。</p>
<p>这个模型的难点在哪？<strong>Skill 使用 Bash 写脚本时，天然带不上用户身份。</strong> 一个 Skill 里 <code>curl https://internal-api/data</code> 这行代码，请求发出去的时候，API 端不知道"这是替张三调的还是李四调的"。身份丢了。这是行业的结构性痛点——当前没有框架原生解决这个问题。</p>
<p><strong>模型二：AI 自有身份。</strong>AI 有一套自己固定的权限和身份（Service Account），调用工具时用的是 AI 自己的凭证。安全控制的焦点变成：谁能使用 AI 本身——你有权调用这个 Agent 吗？</p>
<p>这个模型相对好做——AI 的身份和权限是写死的，不需要运行时透传。但代价是粗粒度：所有用户通过同一个 AI 身份访问资源，无法区分老板查薪资和实习生查薪资。</p>

<h4>悟空的解法：沙箱即身份</h4>
<p>悟空（阿里达摩院）的方案优雅地解决了模型一的透传难题——用沙箱做身份载体：</p>
<ol>
<li>
<p><strong>每个用户绑定独立沙箱</strong>——张三的 Agent 运行在张三的容器里</p>
</li>
<li>
<p><strong>Ingress 层注入身份 Token</strong>——Token 写入沙箱环境（文件系统或环境变量），不是传给 Agent 代码</p>
</li>
<li>
<p><strong>Agent 在沙箱内执行任何操作</strong>——包括 Bash 写新脚本、curl 调 API</p>
</li>
<li>
<p><strong>出站请求经过 Egress 代理</strong>——代理层自动从沙箱环境读取 Token，注入到请求头中</p>
</li>
</ol>
<p>关键设计：Agent 代码完全无感知身份这件事。即使 Skill 用 Bash 写了一段新代码，这段代码发出的请求一样会带上用户身份——因为身份注入发生在网络出口（Egress），不是在代码层。<strong>“沙箱即身份”——身份认证下沉到基础设施层，Agent 代码不接触凭证。</strong></p>
<p>对比传统的长期 API Key（泄露窗口无限），Cloudflare 的 Sandbox Auth（2026 年 4 月发布）使用 OIDC 短期 Token（15-60 分钟有效），即使泄露窗口也极短。</p>
<h4>当前的能力边界</h4>
<p>身份认证是三层里最"展望性"的一层——目前没有框架做到加密身份。所有主流框架（AutoGen、CrewAI、LangGraph、OpenAI SDK）的 Agent 身份都是纯字符串，无加密签名、无 HMAC、无 JWT。非人类身份（NHI）与人类身份的比例已经达到 80:1，多数没有独立认证。</p>
<p>但技术方向已经清楚：ed25519 签名 + HMAC 消息 + 每 Agent 独立 Service Account + JIT 权限。<strong>等框架支持了，设计思路不变——身份在基础设施层解决，不在应用层硬编码。</strong></p>

<p>三个安全策略怎么注册到 HookRegistry 上？31 课我们已经用 <code>hooks.yaml</code> 的 <code>strategies</code> 段声明式加载可靠性策略。32 课的安全策略用同样的方式——但多了一个新能力：<code>deps</code> <strong>依赖注入</strong>。</p>
<p>为什么需要 <code>deps</code>？因为 SandboxGuard 和 PermissionGate 都需要往同一个审计日志里写记录。它们必须共享同一个 <code>SecurityAuditLogger</code> 实例——如果各自 <code>new</code> 一个，审计日志就分散到两个对象里了。</p>

<p>加载器按列表顺序实例化策略，遇到 <code>deps</code> 时从已创建的策略中查找引用。<code>audit: audit_logger</code> 意思是"把构造函数的 <code>audit</code> 参数设置为前面已实例化的 <code>audit_logger</code> 对象"。这就是<strong>声明顺序 = 依赖顺序</strong>的约束——被依赖的策略必须排在前面。</p>
<p><strong>安全策略必须在可靠性策略之前注册。</strong> 为什么？因为 <code>dispatch_gate</code> 在第一个 <code>GuardrailDeny</code> 处就停止——如果一个工具调用包含路径遍历（安全问题），应该在沙箱层就被拦截，不需要再花时间检查预算。</p>
<p>完整的 <code>BEFORE_TOOL_CALL</code> 执行链：<code>sandbox_guard → permission_gate → cost_guard.gate</code>。三道关卡，第一道失败后面不执行。</p>

<p>Task 压迫 LLM：<code>你拥有 shell_executor 工具。必须调用该工具获取当前系统的用户列表</code></p>
</li>
<li>
<p>LLM 在角色禁令与任务压力之间选择了任务——违规调用 <code>shell_executor</code>（LLM 不可靠的证据）</p>
</li>
<li>
<p><code>BEFORE_TOOL_CALL</code> 触发 → <code>dispatch_gate</code> 按注册顺序执行</p>
</li>
<li>
<p><code>sandbox_guard</code> 检查 <code>whoami</code> → 通过</p>
</li>
<li>
<p><code>permission_gate</code> 查 security.yaml → <code>shell_executor: deny</code> → <code>raise GuardrailDeny</code> （Hook 兜底的证据）</p>
</li>
<li>
<p>Adapter 的 <code>pending_deny</code> 存储 → <code>step_callback</code> 重抛 → Crew 终止</p>
</li>
</ol>

<h2>五、避坑指南：最佳实践与反模式</h2>
<h3>🚫 严重破坏安全性的“反模式”</h3>
<ol>
<li>
<p><strong>用 Prompt 管安全。</strong>20 层 harness 实测，22 次失败 19 天内。Agent 写出完美安全计划然后忽略它——确定性门控 ~80% 有效 vs 指令 ~20%。<strong>安全规则必须用代码 / 配置硬编码，不能靠 Prompt 指令。</strong></p>
</li>
<li>
<p><strong>内容过滤 = Agent 安全。</strong> 把安全等同于"过滤不当输出"。Agent 安全的核心是执行控制 + 身份验证 + 可审计性，内容过滤只是表层防线。<strong>Agent 安全 = 限制工具能力边界，不是过滤输出内容。</strong></p>
</li>
<li>
<p><strong>信任 Agent 自己的日志。</strong> 有一个真实案例：安全员审计日志时发现一切正常，但查操作记录时发现 Agent 把有问题的安全日志删了——因为攻击者在注入指令里告诉 Agent"攻击完了以后把日志删掉"。Agent 控制应用层日志，就能抑制或伪造日志。<strong>安全日志必须在 Agent 外部（Hook/ 基础设施层）记录，Agent 不可篡改。</strong></p>
</li>
<li>
<p><strong>默认允许 + 逐项禁止。</strong> 权限系统以允许为默认，只禁止已知危险操作。新工具自动获得全部权限——有一天加了个 <code>shell_executor</code> 你忘了禁止……<strong>Default-Deny：新工具默认无权限，显式授权才能用。</strong></p>
</li>
</ol>
<h3>💡 稳健落地的"最佳实践"</h3>
<ol>
<li><strong>沙箱即身份（Egress Identity Injection）。</strong>Token 写入沙箱环境，出站请求自动注入身份信息。Agent 代码无感知——基础设施层托管认证。</li>
</ol>
<p><strong>落地心法：身份认证下沉到基础设施层，Agent 代码不接触凭证。</strong></p>
<ol start="2">
<li><strong>四层确定性输入消毒。</strong>参照 Claude Code <code>cyberRiskInstruction.ts</code>：环境变量清洗 / 随机 Nonce / 路径归一化 / 元数据剥离。零 LLM 依赖。</li>
</ol>
<p><strong>落地心法：输入消毒用确定性正则规则，不用 LLM 判断——因为 LLM 也可以被绕过。</strong></p>
<ol start="3">
<li><strong>Defense in Depth——没有单点失败。</strong>多层防御，每层独立生效：沙箱 → 权限网关 → 身份认证 → 成本围栏 → 可观测性。</li>
</ol>
<p><strong>落地心法：多层叠加，任何单层被突破时其他层仍有效。别把所有鸡蛋放一个篮子里。</strong></p>
<ol start="4">
<li>**Skill 上架审计 + 运行时 Policy 引擎。** 约 15% 的云端 Skill 藏有木马——上架前自动安全扫描是第一道防线，运行时每步操作实时评估是第二道。</li>
</ol>
<p><strong>落地心法：供应链安全靠双保险，上架审计 + 运行时检查缺一不可。</strong></p>

<h2>课程总结</h2>
<ul>
<li>
<p>我们认清了 Agent 安全与 Chatbot 安全的本质区别——Chatbot 注入最坏是说错话，Agent 注入能删文件、泄数据、发请求。<strong>Agent 安全的本质是限制工具能力边界。</strong></p>
</li>
<li>
<p>我们用 629 次安全测试的数据证明了 Prompt 管不了安全——指令 ~20% 有效 vs 确定性门控 ~80%，四倍差距。<strong>安全不是给 Agent 下命令，是从能力上限制它。</strong></p>
</li>
<li>
<p>我们分析了五类威胁的共同根因——注入、越权、供应链、伪造、外泄，<strong>最终都要通过工具才能做坏事</strong>。</p>
</li>
<li>
<p>我们实现了三层工具能力限制——沙箱限制执行范围（四项配置 + 确定性输入消毒）、权限网关限制工具选择（Deny &gt; Ask &gt; Allow + 密钥工具层注入）、身份认证限制使用主体（两种权限模型 + 沙箱即身份）。所有限制都是确定性的代码 / 基础设施，没有一个靠 Prompt。</p>
</li>
<li>
<p>至此，模块五三层全部就位——30 课看见（可观测）、31 课控制（可靠性）、32 课防御（安全）。</p>
</li>
</ul>
