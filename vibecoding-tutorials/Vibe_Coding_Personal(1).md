# 个人开发者 Vibe Coding 全流程教学文档

## 基于 SDD（Specification-Driven Development，规范驱动开发）· 单人版

> **版本：v1.1**（基于《企业级 Vibe Coding SDD 流程 v2.1》适配；本版完成执行规范化与提示词专业化）
>
> 本文档与企业版的关系：**流程 100% 保留，执行机制单人化。**
> 18+1 个阶段、4 个 Gate、三条贯穿线（安全/质量/变更）全部保留；
> 变化的是：多角色签核 → 单人角色轮换 + AI 虚拟团队 + 冷却期。
>
> 核心原则：**你不是在省略评审，而是在扮演评审者。**
> 一个人开发最大的风险不是写不动代码，而是没有人对你说"这里不对"。
> 本流程的全部设计，都是为了让你一个人也能获得团队级的纠错能力。

# 0. 单人开发适配机制

## 0.1 单人开发的三个特殊风险

企业流程靠"别人"来纠错，单人开发没有"别人"，因此必须把纠错机制写成**可执行、可留痕、可复核**的规则，而不是依赖自觉：

| 风险 | 可观察信号 | 本流程的控制措施 | 必留证据 |
|---|---|---|---|
| **自评放水** | 只写"看起来没问题"，无逐项结论 | 冷却期 + Checklist 机械执行 + AI 独立复审（0.4） | 每项 Pass / Fail / N/A、理由与证据链接 |
| **流程疲劳** | 跳过文档直接编码，或阶段长期不收口 | 时间盒 + 最小可交付物（0.2 机制三）+ 超时升级 | 阶段开始/结束时间、超时项与处置决定 |
| **上下文单一** | 决策没有反例、替代方案或异议记录 | AI 虚拟团队扮演反对者/评审者（0.2 机制二） | 问题、回应、结论和未决项登记 |

凡是无法提供上述证据的检查，一律视为**未执行**，不得用口头确认替代。

## 0.2 三大适配机制

### 机制一：角色轮换（Role Rotation）

你在不同阶段佩戴不同的"角色帽"，并在 Gate 处强制换帽：

```text
构建者（Builder）          评审者（Reviewer）
═══════════════════        ═══════════════════
写业务模型、写提示词、       只看 Checklist，逐条打勾，
指挥 AI 写代码              不看"我当时怎么想的"
        │                          ↑
        └──── 冷却期（按 Gate 规则）────┘
```

执行要求：

- **构建与评审分离**：构建结束时先提交产出版本（Git commit / 文件版本号 / Figma version），评审只针对该固定版本；评审中不得一边发现问题一边静默改稿。
- **冷却期口径统一**：Gate 1 / 2 / 4 至少间隔 12 小时；Gate 3 的单个 PR 可在切换到无关任务 2 小时后评审，但最终准入前必须有一次隔夜复核，且每周至少一次隔夜全量回顾。
- **切换观察视角**：换设备、导出 PDF、使用只读 Diff 或换编辑器任选其一，并在 Gate 记录中注明方式。
- **Checklist 机械执行**：不许写"总体感觉可以"；每项必须记录 Pass / Fail / N/A，Pass 要给证据，Fail 要给修复动作，N/A 要给适用性理由。
- **先记录后修复**：发现问题先登记编号、严重度和归属阶段，再回到构建者身份修复；修复完成后重新生成证据并复核受影响项。

### 机制二：AI 虚拟团队（AI as Virtual Team）

用**独立的新会话**让 AI 扮演团队里的其他角色。关键纪律：

- **评审会话必须全新**：不要把实现会话的上下文带进评审会话。评审 AI 只能看到"设计资产 + 产出物"，不能听到"我当时的意图"——否则它会被你的意图带偏，等于你自己评审自己。
- **一个角色一个会话**：安全评审和产品评审分开开，角色不混。
- **输入使用已固定版本**：向评审 AI 提供输入清单、版本/commit、权威优先级和本次评审范围；不得只粘贴节选后声称完成全量评审。
- **评审 AI 的结论必须逐条回应**：仅允许 `接受`、`驳回（附证据与理由）`、`转 [TBD-*]（附责任人/截止阶段）` 三种处置，不允许默默忽略。
- **AI 不拥有签核权**：AI 提供独立意见；最终结论仍由你负责，并在 Gate 记录中保留差异与裁决依据。

虚拟团队角色表：

| 虚拟角色 | 启用时机 | 职责 |
|---|---|---|
| 产品负责人 | Gate 1、Stage 5 评审 | 挑战业务规则完整性与范围合理性 |
| 魔鬼代言人 | Explore 阶段（Stage 3-6） | 对每个关键决策提反对意见 |
| 架构评审员 | Gate 2 | 挑战架构与契约设计 |
| 安全评审员 | Gate 3 | 按安全清单审查代码 |
| QA 工程师 | Stage 17 | 生成对抗性测试场景、找边界 |
| 发布经理 | Gate 4 | 核对发布就绪度 |

各角色的完整提示词见附录 B。

### 机制三：时间盒（Time-boxing）

每个阶段设上限，到点必须停止扩写并做一次收口检查。**时间盒到期不等于自动通过**：达到最小交付与 DoD 才能进入下一阶段；未达到时必须记录阻塞项，选择缩小范围、补时一次或退回上游，不得静默拖延。

以典型的个人 MVP（2～4 周周期）为例：

| 阶段 | 时间盒 | 最小可交付物（少于此即跳过流程） |
|---|---|---|
| Stage 1-2 环境与规范 | 0.5 天 | 安全基线生效 + project_rules.md 一页 |
| Stage 3-4 市场与竞品 | 1~1.5 天 | 各一份报告，每份 ≤ 3 页 |
| Stage 5 业务建模 | 0.5 天 | BR 清单 + 权限矩阵 + 量化 NFR |
| Stage 6-7 交互与原型 | 1~2 天 | 可点击走通主流程的 Prototype |
| Stage 8-11 工程设计 | 2~2.5 天 | 边界表 + 架构/技术栈 + ER 图 + API 清单 |
| Stage 12-13 PRD 与高保真 | 0.5~1 天 | PRD（含可测试 AC）+ Tokens + 关键页 Figma Design 稿 |
| Stage 14 AI 上下文 | 0.5 天 | AGENTS.md ≤ 300 行 + CLAUDE.md 适配层 ≤ 60 行 + 审计索引 |
| Stage 15-16.5 实现与评审 | 总时间的 40~50% | 代码 + 测试 + Gate 3 记录 |
| Stage 17 联调 E2E | 0.5~1 天 | E2E 报告 + 追溯矩阵 |
| Stage 18 CI/CD 部署 | 0.5~1 天 | 可重复部署 + 回滚方案 |

时间盒超时只允许以下三种记录化处置：`缩小本阶段范围（不得破坏主流程）`、`追加一次明确时长的补时`、`标记阻塞并回溯`。每次处置必须写明原因、影响与新的截止点。

## 0.3 裁剪对照表

流程可以轻量化，但有些环节**砍掉就意味着退出本流程**。

裁剪只能减少篇幅或工具复杂度，不能删除控制目标、证据或追溯关系。任何裁剪都要在对应产出中记录：`裁剪项 / 原标准 / 当前做法 / 风险 / 补偿措施`；未记录的裁剪视为漏做。

### 禁止裁剪（单人同样不可豁免）

```text
✖ 密钥/敏感信息红线（Stage 1 安全基线、secret scanning）
✖ Gate 3 代码评审（冷却期自评 + AI 复审 + 自动化检查）
✖ Task Brief 纪律（每次实现会话明确范围，一个模块一个会话）
✖ 冻结资产不私改（发现上游问题必须标记，不得顺手改）
✖ 测试与追溯（BR → AC → TC 链条，可简化但不可断）
✖ 回滚方案（可以不演练多次，但必须演练过一次）
```

### 可以简化（相对企业版）

| 环节 | 企业版 | 单人版 |
|---|---|---|
| Gate 签核 | 产品/技术/设计/安全多人签字 | 本人冷却期自评 + AI 角色复审，记录照填 |
| 变更控制 CCR | 分级评估 + 重走 Gate | 简版三级处理（附录 C），L3 强制隔夜 |
| 文档规模 | 各阶段完整规格 | 满足"最小可交付物"即可，但要素不缺 |
| CI/CD | 多环境多阶段流水线 | 单条 GitHub Actions + dev/prod 两环境 |
| 监控告警 | 指标+告警+接收人体系 | 免费 uptime 监控 + 错误追踪各一 |
| SBOM/安全扫描 | 完整 SBOM + 多工具 | 依赖审计 + secret scan + 一个 SAST |
| PRD | 十要素完整 PRD | 保留要素但篇幅不限，AC 不可省 |

## 0.4 单人 Gate 评审协议

四个 Gate 全部保留（Gate 1 产品冻结 / Gate 2 工程冻结 / Gate 3 代码准入 / Gate 4 发布就绪），单人执行协议：

```text
第一步：固定评审基线
  → 记录待评审文件、版本/commit、上游权威资产及其状态
  → 评审开始后，任何修改都生成新版本，不覆盖基线

第二步：构建者自查
  → 对照本阶段 DoD 与 Gate Checklist 逐项填写 Pass / Fail / N/A
  → 每项附文件锚点、命令输出、截图或可复现步骤之一

第三步：执行冷却期并换帽
  → Gate 1 / 2 / 4 ≥ 12 小时；Gate 3 按 0.2 的例外规则执行
  → 记录间隔时长与视角切换方式，再以评审者身份只读检查

第四步：AI 独立复审
  → 全新会话，使用附录 B 对应角色提示词
  → 只提供上游权威资产、固定版本产出和 Gate Checklist
  → 对 AI 问题逐条处置：接受 / 驳回（附证据）/ 转 TBD（附责任与期限）

第五步：裁决、复验与归档
  → 阻塞项清零后重新运行受影响检查，更新证据
  → 参与人：本人（构建）/ 本人（评审）/ AI（独立复审）
  → 结论只允许 APPROVED / CONDITIONAL / REJECTED
```

**问题与结论口径：**

- `阻塞（Blocking）`：影响核心流程、权威资产一致性、安全/隐私、可测试性或后续阶段输入可靠性；未关闭时不得 `APPROVED`。
- `非阻塞（Non-blocking）`：不影响下阶段正确消费；必须有责任人、截止阶段和跟踪位置。
- `APPROVED`：所有准入项通过、阻塞项为 0、证据齐全；指定资产可冻结并进入下一阶段。
- `CONDITIONAL`：阻塞项为 0，但仍有已登记的非阻塞项；只有对应 Gate 明确允许时才能开展不依赖该项的工作，资产暂不视为完全冻结。
- `REJECTED`：存在阻塞项、证据缺失或权威资产冲突；必须回溯指定阶段。Gate 1 进入 Stage 8 的条件仍是 `APPROVED`。

## 0.5 AI 提示词工程规范（与企业版一致）

所有执行型和评审型提示词统一采用以下六段式；不得省略段落，只能写明“不适用”及理由：

```text
① 角色与能力边界
   说明专业角色、负责范围、无权决定的事项，以及何时必须停止。
② 权威输入
   列出路径/链接、版本或状态、优先级；高优先级覆盖低优先级，
   但冲突不得静默合并。未提供的输入明确写“缺失”。
③ 任务与输出契约
   写清目标、执行顺序、固定输出路径、格式/字段、编号规则和验收标准；
   修改已有文件时列出允许修改范围。
④ 约束
   分别列出“必须”“禁止”“范围外”；冻结资产、安全红线和工具限制放在此处。
⑤ 不确定与冲突处理
   信息缺失用 [TBD-类别]，资产矛盾用 [CONFLICT]；每项写明影响、
   所需决策、责任人/确认阶段。禁止猜测、补造数据或自行裁决冲突。
⑥ 证据与完成前自检
   每个关键结论给来源或可复现证据；逐项输出 Pass / Fail / N/A，
   Fail 不得宣称完成，N/A 必须说明理由。
```

**统一响应尾部（所有提示词均应要求 AI 输出）：**

```text
1. 变更摘要：做了什么、明确没做什么
2. 产出清单：路径/链接、版本、状态（Created / Updated / Unchanged）
3. 未决与冲突：全部 [TBD-*] / [CONFLICT]，无则写“无”
4. 证据索引：结论 → 来源/文件锚点/命令与退出码/截图
5. Self-Check：逐项 Pass / Fail / N/A（含理由）
```

**标记纪律：** `[TBD-*]` 表示输入不足、需由指定责任域确认；`[CONFLICT]` 表示两个及以上权威资产互相矛盾；`[MISSING-SOURCE]` 表示声明的来源不可访问；`[DERIVED]` / `[DERIVED-VISUAL]` 只表示可由已引用事实复算的推导，不可替代缺失来源。所有标记必须按附录 F 编号、登记影响、责任人、证据和最晚关闭阶段；影响当前输出正确性的项为阻塞项。

上下文预算规则（单人同样适用，因为限制来自模型而非人数）：

- 单个分析/执行批次直接加载的权威文档 ≤ 5 份（当次 Task Brief 与来源索引不计）；超出时必须分批、记录已读章节与版本，其余只保留路径引用
- 单份超 300 行只传相关章节
- **实现类任务一个模块一个新会话**，以 Task Brief（附录 E）开场
- `AGENTS.md` ≤ 300 行并作为唯一工程规则权威；`CLAUDE.md` ≤ 60 行且只做运行时适配；细节一律路径引用

# Phase 1：基础搭建

## Stage 1：基础环境配置

### 目标

建立**项目级、可验证、可回滚**的 AI 辅助开发环境与安全基线。个人项目最常见且代价最高的事故之一，是把 API Key 提交到仓库；本阶段要把防线变成配置、扫描与证据，而不是一句“我会注意”。

### 个人执行要点

- 时间盒：2 小时
- **准入与权威输入**：项目根目录、实际使用的 AI Coding 工具、已确定技术栈及现有项目级配置；技术栈未定时不得预装“可能会用”的 MCP。
- **你做什么**：确认工具与框架选型、授权外部服务配置、复核扫描结果；任何真实凭证只由你在受控环境中注入。
- **AI 做什么**：只检查与修改项目级配置，执行脱敏后的连通性/安全测试并形成报告；不得读取、回显或写入真实密钥。
- **执行顺序**：现状盘点 → 变更计划 → 项目级配置 → 连通性验证 → secret 扫描 → 证据归档。任一步失败先记录，不得用后续步骤掩盖。
- **固定产出**：`docs/00_setup/environment_baseline.md` + 适用的项目级配置文件 + `.gitignore` + `.env.example` + secret scanning / pre-commit 配置。
- **退出条件**：本节质量门禁全部 Pass；不适用项必须有 N/A 理由，任何阻塞型 `[TBD-INFRA]` 未关闭时不得进入 Stage 2。
- LangChain 仅作为示例：使用 LangChain/LangGraph 时可接入 `docs-langchain` + `reference-langchain`；其他项目必须替换为**所用技术栈的官方来源**，步骤与证据标准不变。

# Phase 2：Product Discovery / Business Design

## Stage 3：市场调研

### 个人执行要点

- **阶段目标**：用可核验事实判断“问题是否真实、是否值得现在投入”，而不是写行业白皮书。
- 时间盒：半天；到点优先收敛结论与未知项，不继续堆资料。
- **准入与权威输入**：明确的项目领域、目标地区/人群、预期使用场景和个人约束；缺失时先登记 TBD，不以泛行业数据代替。
- **执行顺序**：定义研究问题与口径 → 检索一手/可信二手资料 → 交叉验证关键主张 → 区分事实/推论 → 魔鬼代言人挑战 → 收敛 Go / Revise / Stop 建议。
- **职责分工**：AI 做检索、归类与初稿；你必须打开原始来源，人工复核所有决定立项的数字与引用。
- **固定产出**：`docs/01_market_research/market_research_report.md`，正文 ≤ 3 页；证据索引与挑战记录可作为附录，不计入正文页数。
- **退出条件**：关键主张有证据、反证与置信度；阻塞型 `[TBD-RESEARCH]` / `[CONFLICT]` 为 0；质量门禁全部 Pass。

```text
P1. 我确认的研究边界：项目领域={填写}；地区={填写}；目标人群={填写}；

- [ ] 魔鬼代言人的每个问题已接受、驳回（附证据）或转 TBD
- [ ] 报告正文不超过 3 页，且未越界做 Stage 4/5 的决定
```

## Stage 4：竞品拆解

### 个人执行要点

- **阶段目标**：用同一任务与同一时间口径比较现有解法，识别可验证的空白，而不是罗列功能。
- 时间盒：半天到一天；竞品 2~3 个即可，至少包含 1 个直接竞品和 1 个替代方案。
- **准入与权威输入**：Stage 3 已通过质量门禁；竞品候选与选择标准已明确。
- **执行顺序**：定义对比任务/维度 → 固定版本与价格快照 → 走查核心流程 → 收集官方事实与真实反馈 → 横向比较 → 提炼可验证差异点。
- **固定产出**：`docs/02_competitor_analysis/competitor_analysis_report.md`，正文 ≤ 3 页；证据附录不计页数。
- **退出条件**：每个结论均有事实证据或明确标为推论；差异化能直接输入 Stage 5，质量门禁全部 Pass。

### 提示词

```text

提出可验证机会，不得假装实际使用过无法访问的产品，不得把营销文案当用户效果，

③【任务与输出契约】
```

## Stage 5：业务建模

### 目标

把调研收敛为结构化业务模型。**这是全流程最重要的资产，个人项目同样不例外**——它是你三个月后判断"AI 写得对不对"的唯一标尺。

### 个人执行要点

- 时间盒：半天
- **准入与权威输入**：Stage 3/4 质量门禁通过；你的立项目标、资源上限与必须遵守的政策已确认。
- **执行顺序**：锁定目标/边界 → 建流程/实体/状态/权限 → 编写 BR → 量化 NFR → 划定 MVP/OOS → 建追溯 → AI 产品负责人独立挑战 → 逐条处置。
- NFR 按个人项目现实设定（例：“目标负载下核心接口 P95 < 500ms”），每项同时写测量条件与方法；不追求虚假的企业级数字。
- **固定产出**：`docs/03_problem_modeling/business_model.md`，它在 Gate 1 后成为下游业务规则权威源。
- **退出条件**：模型内部一致、每条规则可测试、挑战问题已处置，质量门禁全部 Pass。

### 提示词

```text
①【角色与能力边界】
你是负责把探索证据收敛为可测试业务规格的业务架构师。你可以结构化已确认目标、
提出待确认候选并检查一致性；你不得把研究推论直接升级成业务规则，不得替我决定
商业政策、权限、合规结论或 MVP 取舍。

②【权威输入】
P1. 我明确确认的产品目标、约束、资源上限与决定记录：{填写；缺失写“缺失”}
P2. docs/01_market_research/market_research_report.md（已通过 Stage 3）
P3. docs/02_competitor_analysis/competitor_analysis_report.md（已通过 Stage 4）
P4. 适用的法律/平台/合同硬约束（如有，必须引用原文位置）
P5. 本文档 Stage 5 要求
研究报告是证据，不自动拥有业务决策权；P2/P3 中未被我确认的建议只能作为
`候选` 或 [TBD-BIZ]，不能直接写成 BR。

③【任务与输出契约】
固定输出 docs/03_problem_modeling/business_model.md，使用以下结构：
1. 文档元数据：版本、状态 Draft、as-of date、输入版本、Owner；
2. 业务目标 OBJ-001...：用户/业务结果、基线、目标值、时间窗口、测量方式；
3. MVP 与 Out of Scope：每项有边界、理由、重新纳入触发条件；必须覆盖 Stage 3/4
   提到的相邻能力，不得用“其他、等等”兜底；
4. 核心流程：Mermaid 展示触发、人工/系统节点、输入、处理、输出、失败/补偿路径；
5. 实体与关系：ENT-001...，只定义业务含义、标识、生命周期和关系，不提前设计表；
6. 角色与权限矩阵：ROLE-001... × 资源/动作，使用 Allow / Deny / Conditional，
   默认拒绝，Conditional 必须引用 BR；
7. 状态模型：STATE-xxx、合法转换、触发者、前置条件、失败处理与终态；
8. 业务规则 BR-001...，每条固定字段：规则陈述、来源/目标、Actor、Trigger、
   Preconditions、Inputs、Decision/Action、Outcome、Exceptions、可测试示例；
9. NFR-001...：至少评估性能、容量、可用性、安全/隐私、数据保留与可观测性；
   每条写指标、目标/阈值、适用范围、测量环境、验证方法和验证阶段。不适用须说明；
10. 追溯矩阵：OBJ → MVP 能力 → BR/NFR → 来源 EV/DIF；
11. 产品负责人挑战记录：问题、严重度、我的处置、修改位置、状态；
12. TBD / CONFLICT 登记与术语表。
生成后做一致性检查：流程动作是否有权限、状态转换是否有 BR、MVP 能力是否有目标与
规则、NFR 是否能在个人项目环境中测量。

④【约束】
必须：BR/NFR 编号唯一且不复用；规则使用可观察条件和结果；权限默认拒绝；所有 NFR
量化并给测量方法；建议与已确认规则分开。
禁止：自行新增角色、收费/配额/审核等商业政策；使用“等、相关、适当、尽快、高性能、

范围外：页面布局、视觉、技术架构、数据库 schema 与 API 字段。

⑤【不确定与冲突处理】
未确认的业务决定登记 [TBD-BIZ-nnn]，包含问题、候选、影响范围、Owner 与 Gate 1 前
关闭条件；安全/合规事实未确认时按相应 TBD 登记，不得给肯定结论。输入资产矛盾时

⑥【证据与完成前自检】
最终按 0.5 的统一响应尾部输出，并逐项检查：
- [ ] OBJ、BR、NFR、角色、实体和状态 ID 唯一、无断号复用
- [ ] 每个 MVP 能力可追溯到 OBJ 和至少一条 BR；每条 BR 有来源与可测试示例
- [ ] 每个流程动作有权限结论，每个状态转换有触发、前置条件与失败处理
- [ ] 每条 NFR 有阈值、条件、测量方法和验证阶段；N/A 有理由
- [ ] Out of Scope 覆盖 Stage 3/4 出现但未纳入 MVP 的相邻能力
- [ ] 产品负责人挑战意见已逐条处置，未静默忽略
- [ ] 无模糊词替代规则，无研究建议被擅自升级为 BR
任一项 Fail 时不得声称 Stage 5 完成。
```

## Stage 6：核心交互设计

### 冲突优先级

```text
Business Model > Interaction Design > Prototype > Architecture > Figma
```

- 高优先级资产只约束其权威范围：Business Model 决定业务规则与权限，Interaction Design 决定已确认的交互行为，Prototype 只证明行为呈现。低优先级资产不得覆盖高优先级事实。
- 同层存在多个版本时，只使用明确标记为 `APPROVED` 的基线；若没有已批准基线，不以文件修改时间猜测有效版本。
- 发现冲突时不得修改 Gate 1 冻结资产，也不得在下游“合理化”冲突。记录 `[CONFLICT]`、双方证据和影响，并暂停受影响的设计；只有用户确认或按附录 C 完成上游变更后才能继续。
- 信息缺失使用对应的 `[TBD-*]`；可逆且不影响契约/安全的设计假设可标记 `[ASSUMPTION]`，并写明验证方法。不得把假设写成既定事实。

## Stage 10：数据模型

### 个人执行要点

- 时间盒：半天
- 准入条件：Stage 8 架构质量门禁通过，Stage 9 已明确数据库与数据访问方案；影响物理模型的数据技术选型不得保留为 `[TBD-INFRA]`。

## Stage 13：Figma High-Fidelity UI 设计

### 定位

**Stage 13 负责"已经验证过的 UX，最终长什么样"，并产出 Design System。**

它不是再做一遍 Prototype，也不是 Production UI。

```text
Stage 6  Interaction Design     = 页面 / 流程 / 状态矩阵（行为规格）
Stage 7  Figma Make Prototype   = 可点击验证"产品怎么工作"（行为保真）
Gate 1   Prototype Review       = 行为冻结
Stage 12 PRD                    = AC / 权限 / 异常的可测试清单（可与本阶段并行）
Stage 13 Figma Design + Tokens  = 视觉系统 + 可交付高保真（视觉保真）
Stage 16 Figma MCP + Cursor     = Production UI（实现保真）
```

2026 年的工具分工（用错工具是本阶段最大的浪费）：

| 工具 | 本阶段角色 |
|---|---|
| **Figma Make** | **不要再用。** 它属于 Stage 7：prompt → functional prototype。继续在 Make 里抠 1px / 换品牌色，等于用原型工具冒充 Design System |
| **Figma Design / Figma Agent** | **本阶段主场。** 在 Design canvas 上生成/修改设计、套用 Design System、给设计反馈 |
| Figma Prototype | 可把高保真画板串成演示，但不替代 Tokens / 组件规格 |
| **Figma MCP + Cursor / Codex** | **下一阶段。** 本阶段只准备可被 MCP 读取的 Design 文件 + tokens + component_spec |

```text
              AI
               │
        ┌──────┴──────┐
        ↓             ↓
   Figma Make    Figma Agent
   (Stage 7)     (Stage 13)
        │             │
        ↓             ↓
 Functional       Actual Design
 Prototype        + Design System
        │             │
        └──────┬──────┘
               ↓
        High-Fidelity 冻结
               ↓
     Figma MCP → Stage 16 代码
```

**最关键的一条：不要让 AI 从 PRD 直接生成 Production UI。**  
PRD 没有视觉系统，Make 没有 Design Tokens。跳过本阶段，前端会变成"看起来能用、但 Token/组件/状态对不齐"的一次性界面。

### 个人执行要点

- 时间盒：0.5~1 天（与 Stage 12 合计；Tokens + 关键页即可，不要追求整站精修）
- **直接裁剪成熟组件库**（shadcn/ui、Ant Design 等）的默认 Tokens，不要从零发明颜色和字号——个人项目的竞争力在产品逻辑，不在像素
- 高保真稿可只精修**关键页面**，但状态覆盖不可抽样：未单独出稿的页面/状态必须在 `highfi_page_map.md` 中声明复用的组件、画板与证据，不能用“后续补”代替结论
- 发现业务/流程不对：**停止画视觉**，按附录 C 回溯，禁止用新画板掩盖 Gate 1 已冻结的行为错误
- 每张交付画板统一命名为 `PG-xxx / 页面名 / Viewport / State`；每个组件集统一命名并绑定 `component_spec.json` 中的组件 ID，避免代码阶段靠肉眼猜对应关系
- 任何“已覆盖”“已使用 Token”“与原型一致”的结论，都必须能定位到文档章节、Figma page/frame/component 名称或 node ID；仅凭截图印象不得判通过
- 设计文件不可访问或 Figma Agent 无法读取指定节点时，必须标记 `[MISSING-SOURCE]`，不得声称已核对

### 前置条件

- Gate 1 = APPROVED（`docs/05_prototype/prototype_review.md`）
- Gate 2 = APPROVED（`docs/07_backend_design/gate2_review.md`；否则页面结构 / API 边界还可能变，视觉会返工）
- Stage 12 可并行：PRD 未完成时，先用冻结的 Interaction + Prototype 出映射和关键页；`prd_document.md` 落地后用 AC 补状态覆盖，**禁止在无 PRD 时发明新功能**
- Stage 9 的 `docs/07_backend_design/technology_stack_spec.md` 已冻结 UI 组件方案及确切版本；未选定或无来源时不得生成最终 Tokens
- 准入不满足时，本阶段状态只能是 `Blocked`，允许产出缺口/映射草案，不允许冻结高保真资产

### 13.2 继承什么、本阶段才决定什么

**必须原样继承（改了就等于推翻 Gate 1）：**

- 信息架构、侧栏/导航信息、页面清单与 PG 编号
- 页面区块关系（例如 Chat 工作区 + Task Panel，谁主谁辅）
- 主流程、跳转、危险操作确认
- 状态矩阵里判定为适用的状态（Default / Loading / Empty / No Result / Error / No Permission / Editing / Submitting / Success-Failure）
- PRD AC 要求用户能看见的成功 / 失败 / 空 / 错 / 无权限
- Desktop 1440px + Mobile 375px 的核心任务不断裂
- 角色可见性、字段必填/只读/禁用规则、后端错误到 UI 状态的映射

**明确丢掉（Make 的皮肤，不是设计系统）：**

- Prototype 的颜色、字体、阴影、圆角、装饰插画
- 为了"尽快能点"而堆的一次性控件外观（可换成库组件，但交互语义不变）

**本阶段才允许决定：**

- Color / Typography / Spacing / Radius / Shadow / Icon
- Button / Input / Card / Table / Modal / Dropdown / Sidebar / Navigation 的 variants 与 states
- Design Tokens 与组件规格
- 在不改变 IA 与流程的前提下，收紧排版、层级、密度
- 视觉可访问性与响应式实现细节；若改变可见行为或字段语义，则不属于视觉决定，必须回溯

### 13.3 操作步骤（先对照，再画，再导出给代码）

不要一上来就打开 Figma Make 继续 prompt。按下面 7 个编号步骤（Step 0～6）执行，每步一个会话（或 Figma 内一次明确任务）。

**Step 0 — 资产对照（Cursor / Claude，先出映射表）**

把 Prototype 画板、PG-xxx、状态矩阵、PRD AC 对成一张双向可追溯表，再决定“哪些页必须出高保真”。产出：`docs/09_figma_highfi/highfi_page_map.md`。该文件必须包含状态/AC 覆盖率、来源证据、复用目标和阻塞项；提示词见 **13.4 Prompt A**。

**Step 1 — 裁剪 Design Tokens（不要从零发明）**

读取 `docs/07_backend_design/technology_stack_spec.md` 中 Stage 9 已冻结且版本明确的 UI 组件方案（如 shadcn/ui），只保留本产品用到的 Color / Typography / Spacing / Radius / Shadow。产出：`docs/09_figma_highfi/design_tokens.json`；必须是合法 JSON，每个 Token 带 `$type`、`$value`、来源/映射，引用关系不得悬空。提示词见 **13.4 Prompt B**。

**Step 2 — 组件规格（只定义实际会用的）**

对照页面映射里出现的控件，定义 component ID、anatomy、variants、interaction states、validation states、responsive behavior、accessibility 与 Token 引用。产出：`docs/09_figma_highfi/component_spec.json`；禁止出现未定义 Token 或未映射组件。提示词见 **13.4 Prompt C**。

**Step 3 — 在 Figma Design 里铺关键页（Figma Agent，不是 Make）**

新建或打开 **Figma Design** 文件（不要在 Make 文件上继续迭代）。把 Tokens 与组件套到关键页；布局以 Prototype 的 IA 为骨架。一次只处理一个页面或一条完整流程，完成后记录 Page / Frame / Component 名称及 node ID。提示词见 **13.4 Prompt D**。链接与节点索引写入 `docs/09_figma_highfi/figma_highfi_design_link.md`。

**Step 4 — 按状态矩阵 + AC 补画板**

不为“看起来完整”加新页面；只补 `highfi_page_map.md` 中标记 `HF 必画`、但 Step 3 尚无证据的状态。每补一个状态就回写画板名/node ID 与 AC 映射；提示词见 **13.4 Prompt E**。

**Step 5 — 走查（换帽，对照 Prototype / PRD，不看感觉）**

在全新会话中用 **13.4 Prompt F** 做独立走查，逐条输出 Pass / Fail / N/A 与可定位证据，记录写入 `docs/09_figma_highfi/highfi_review.md`。不得由“生成画板的同一上下文”自评通过；阻塞项为 0 且所有覆盖率达标后才冻结视觉资产。

**Step 6 — 交给 Stage 14 / 16**

冻结物只有这些（不要另造一份"设计说明小说"）：

```text
docs/09_figma_highfi/highfi_page_map.md
docs/09_figma_highfi/figma_highfi_design_link.md   ← Design 文件，不是 Make 链接
docs/09_figma_highfi/design_tokens.json
docs/09_figma_highfi/component_spec.json
docs/09_figma_highfi/highfi_review.md
```

以上 5 份资产必须互相引用同一组 PG、AC、Token、component ID 与 Figma node；任一链接失效、JSON 无法解析或 ID 悬空都不得交接。Stage 16 用 Tokens + component_spec 约束代码；若已接入 Figma MCP，再让 Agent 读取 Design 文件核对间距与组件，而不是重新发明 UI。

#### Prompt A：资产对照 / 页面映射（Cursor）

```text

- 不新增规范外的页面、功能、业务规则
- 不在前端做权限最终判定（判定以后端为准）
- 不绕过共享组件自行实现
- 不做无关重构、批量格式化、依赖升级或测试阈值调整
- 不通过快照盲目更新、跳过测试或弱化断言来消除失败
- 不声称读取了不可访问的 Figma 资产，不臆测视觉值、接口字段或验证结果

【失败与回退】
- 规范/资产冲突：报告 [CONFLICT]、冲突位置、影响 PG/AC 和所需决策
- 命令失败：保留原始错误与退出码；同一路径连续失败 2 次后停止试错，
  报告已尝试动作和下一步最小建议
- 工具或浏览器不可用：标记 [NOT RUN] 并给出可复现命令，不得判为通过
- 无法在本会话消除回归：回退本会话相关改动，不触碰用户既有改动

【完成定义（DoD）】
- [ ] Task Brief 内 PG/AC 实现率 100%，范围外路由、页面和行为未改变
- [ ] highfi_page_map 标记适用的页面九态均可复现；每个 N/A 均有上游证据
- [ ] API 路径、字段、状态码和错误分支与 Contract 一致，相关测试 100% 通过
- [ ] 视觉值来自 Tokens/组件规格；无新增硬编码颜色、字号、间距
- [ ] 关键流程可键盘操作，既有无障碍检查无新增 error
- [ ] lint、类型检查、组件/页面测试和生产构建均 0 error

【最终输出——固定格式】
1. 范围与结论：DONE / PARTIAL / BLOCKED
2. 变更文件：逐文件目的；附精简 diff 统计与行为/视觉差异
3. 追溯：PG/状态/AC/API → 组件或路由 → TC-xxx
4. 验证证据：命令、退出码、通过/失败数、构建结果；可用时附截图/差异
5. 偏离、遗留、风险与回退方式
6. 自检：逐条回应 DoD；未知项标 [UNKNOWN]，未执行项标 [NOT RUN]
7. 将同一份报告保存至 docs/11_test/implementation_reports/{TASK-BRIEF-ID}.md；
   文件不存在或未保存时不得宣称本 Task Brief 已完成
```

### 质量门禁

- Task Brief 范围内 PG/AC 与实际 diff 一致；范围外文件变更 = 0（必要生成文件须说明）
- 适用页面状态实现与可复现率 100%；关键流程、组件/页面测试通过率 100%
- API Contract 字段、状态码与错误分支一致率 100%，缺失/臆造字段 = 0
- 新增硬编码颜色/字号/间距 = 0；视觉来源可追溯至 Tokens、组件规格或 Figma Design
- lint、类型检查、测试、生产构建 0 error；无障碍检查无新增 error
- `docs/11_test/implementation_reports/{TASK-BRIEF-ID}.md` 包含 diff 摘要、命令退出码、验证证据、风险与回退；必需证据缺失不得进入 Stage 16.5

## Stage 16.5：代码评审门禁（Gate 3）——单人版最重要的 Gate

### 为什么单人更不能省

企业里 AI 代码至少还有同事看一眼；单人项目里，**如果你不看，就是没人看**。本 Gate 用三层替代"同事"：

```text
第一层：CI 自动化检查（机器评审，每次 push）
  lint → 格式/类型检查 → 测试/覆盖率 → 构建 → 安全扫描 → 契约比对
  每项保留与 commit SHA 绑定的日志、报告或制品，失败即阻断合并/发布

第二层：冷却期自评（换帽评审）
  代码写完至少隔夜，按附录 D Checklist 逐条审查自己的代码
  ——从目标分支到候选 commit 的完整 diff 审查，逐条记录“通过/问题/不适用”及证据

第三层：AI 独立复审（全新会话）
  使用附录 B.4 安全评审员角色；输入仅限 Task Brief、冻结资产、完整 diff、
  CI 结果与必要代码上下文；AI 只提出带文件/位置/证据的问题，不直接改代码
```

### CI 自动化检查配置提示词

```text
【角色】
你是 CI 质量与供应链安全工程师。只配置与仓库现有技术栈匹配的最小流水线，
不修改业务代码，不用新增工具掩盖现有失败。

【输入】
AGENTS.md（唯一工程规则权威；CLAUDE.md 仅为适配层）、依赖锁文件、现有脚本与 workflow、Task Brief、
API Contract、测试与覆盖率配置。未知内容必须先只读核验。

【任务】
为当前项目新增或最小化修改 GitHub Actions 质量流水线，并输出验证证据。

【启动协议】
1. 识别真实语言/版本、包管理器、锁文件、现有脚本、默认分支和已有 workflow
2. 输出“检查项 → 仓库命令 → 触发条件 → 阻断阈值 → 证据制品”的计划
3. 命令或阈值无仓库依据时标记 [UNKNOWN] 并请求确认，不得自行发明
4. 保留已有有效检查；只做完成下列目标所需的最小 diff

【必须覆盖】
1. Lint 与格式检查（0 error）
2. 静态类型检查（0 error）
3. 单元、接口及适用的前端测试全部通过，生产构建成功
4. 覆盖率：核心 BR/AC 路径有用例；整体行覆盖率 ≥ 70% 或仓库既有更高阈值，
   且不得低于合并前基线
5. 安全扫描：SAST、依赖漏洞、secret 扫描；严重/高危 = 0，
   中低风险须有处置记录、责任人与期限
6. 契约一致性：有机器可读契约时执行自动 diff；否则生成明确的人工复核项，
   不得把无法自动比对表述为“已通过”
7. 报告与可追溯性：测试、覆盖率和安全报告关联 commit SHA；失败日志可下载

【安全与可靠性约束】
- 触发器覆盖 pull_request 和受控的 push；失败 job 阻断后续构建/发布
- permissions 默认只读、按 job 最小授权；第三方 Action 固定到可信版本或 commit SHA
- 使用锁文件确定性安装；缓存键包含锁文件哈希，禁止缓存或打印 secrets
- 设置 timeout 与同分支 concurrency；取消过期运行，避免重复部署
- 不引入无关工具、不静默跳过失败，不通过降低阈值让流水线变绿

【验证与输出】
- 校验 workflow 语法，并尽可能在本地运行等价命令
- 固定输出：变更文件/diff 摘要、每个 job 的目的与依赖、完整命令与退出码、
  阈值、权限、缓存、制品、[NOT RUN] 项、风险及回退方式
- 未实际触发远端 CI 时明确写 [NOT RUN]，给出触发和验收步骤，不得声称 CI 已通过
```

### 质量门禁（全部可度量）

- 候选 commit SHA 的必需 CI 全绿：lint/format/type/test/build = 0 error，测试失败/跳过 = 0（规范批准的跳过除外），覆盖率达到阈值且不低于基线
- SAST/依赖扫描严重与高危未处置项 = 0，secret 告警 = 0；中低风险均有责任人、处置期限和发布影响判断
- 可自动比对的契约多余/缺失端点与字段 = 0；不可自动比对项已人工复核并附证据
- 冷却期后按附录 D 完成全量 diff 自评，Checklist 回答率 100%，每个问题均有文件/位置和处置结论
- AI 复审发现逐条归类为“已修复/误报（附证据）/接受风险（附理由与期限）”；阻塞/严重问题未关闭数 = 0
- `docs/11_test/code_review_report.md` 记录 Task Brief、评审范围、目标/候选 commit、diff 统计、CI 链接或日志、发现项、修复验证、剩余风险和 Gate 结论
- Gate 3 结论遵循 0.4 节口径；只有 `APPROVED` 才可进入 Stage 17。任一必需检查 `[NOT RUN]`、证据缺失或范围漂移均为 `REJECTED`，回到对应 Stage 修复后重新评审

# Phase 8：验证与交付

## Stage 17：前后端联调 / E2E 验证

### 个人执行要点

- 时间盒：0.5~1 天
- 先用 **AI QA 工程师角色**（附录 B.5）生成对抗性测试场景清单（并发、重复提交、异常输入、越权尝试），再逐条执行——单人最大的测试盲区是"只测自己想到的路径"
- 只验证 Gate 3 = `APPROVED` 的候选 commit；固定环境版本、配置基线和可重复测试数据，报告必须能回答“测了哪个版本、在哪测、如何复现”
- 自动化优先，人工场景也要记录步骤、期望、实际结果与证据；失败用例不得靠重跑改成通过，先判定产品缺陷、测试缺陷、环境问题或 flaky

### 提示词

```text
【角色】
你是独立的资深测试架构师。你的目标是用可复现证据判断发布候选是否满足
冻结 AC/NFR，而不是帮助实现方证明“看起来能用”。

【输入】
完整 Task Brief、AGENTS.md、docs/10_ai_context/ai_context_index.md、
docs/11_test/test_plan.md、Gate 3 的 APPROVED 记录、候选 commit SHA/构建制品、
测试环境与脱敏测试数据说明。不要一次加载“全部冻结资产”：先依据追溯矩阵定位
当前测试批次所需章节，每批直接加载不超过 5 份权威文档并记录版本。

【任务】
为当前发布候选设计并执行端到端联调验证，输出 docs/11_test/e2e_report.md。

【启动协议】
1. 只读核验候选 commit、环境地址/版本、依赖服务、测试账号、数据重置方式、
   健康状态及 Gate 3 结论；任一关键前提缺失则标记 [BLOCKED]
2. 将 BR → AC/NFR → API/权限 → TC/E2E 建立追溯矩阵，先列覆盖缺口
3. 输出执行顺序、测试数据、预期结果、证据位置和退出/清理条件
4. 仅在授权测试环境执行安全场景；使用非破坏性 payload，不触碰真实用户数据

【验证范围】
1. 核心业务流程（对照 AC-xxx 逐条，覆盖跨页面/服务的数据闭环）
2. 权限（对照权限矩阵逐角色）
3. 正常/异常/空/超时/重试状态及 API Contract 一致性

5. 安全回归：未认证、横向/纵向越权、输入注入、敏感字段与错误信息泄露
6. 性能冒烟：在固定负载和样本量下核对核心接口的 NFR-xxx 阈值
7. 可恢复性冒烟：适用时验证依赖短暂不可用后的超时、降级或恢复行为

【追溯要求】
- 每个 E2E-xxx 关联 BR/AC/NFR/API/角色，并记录前置条件、数据、步骤、
  期望、实际、耗时、结果（PASS/FAIL/BLOCKED）和证据
- 输出追溯矩阵：BR → AC/NFR → TC/E2E → 结果；核心条款无覆盖即阻塞

【问题处理】
标记归属：Business / Interaction / Frontend / Backend / API Contract /
Infrastructure / Test。记录严重度、复现率、最小复现步骤、证据、影响范围和
建议责任阶段；不直接修改实现或上游业务规则，变更走附录 C。

【失败与重测规则】
- 首次失败保留日志、截图/录屏、请求标识和测试数据，不覆盖证据
- 修复后只在新候选 commit 上重测失败项，并回归受影响核心路径
- 环境问题标 [BLOCKED]，flaky 必须连续稳定通过既定次数后才能关闭；
  未达到条件不得改记 PASS
- 工具不可用或未执行项标 [NOT RUN]，不得推断结果

【最终输出——固定格式】
1. 候选版本、环境、时间窗、配置基线与数据集
2. 执行摘要：总数及 PASS/FAIL/BLOCKED/NOT RUN 数量、核心流程通过率
3. BR/AC/NFR/API 追溯矩阵与覆盖率
4. 缺陷清单：严重度、复现步骤、证据、归属、阻塞发布与否
5. 性能/安全/权限/数据一致性结果及原始证据位置
6. 重测与回归结果、已知限制、剩余风险
7. 结论：PASS / FAIL；不得输出带条件的模糊“基本通过”
```

### 质量门禁

- Gate 3 = APPROVED，候选 commit/制品与 E2E 报告一致；测试环境、数据和命令可复现
- 核心 BR/AC 流程执行率与通过率均为 100%；阻塞/严重/高危安全缺陷未关闭数 = 0
- BR/AC 追溯覆盖率 100%；适用 NFR、角色权限和 API 覆盖率 100%，缺口均阻塞
- 自动化和人工场景的 FAIL/BLOCKED/NOT RUN = 0；规范批准的例外须有负责人、期限和发布影响判断
- 性能结果满足对应 NFR 的负载、样本量和阈值；无阈值时只能标 `[UNKNOWN]`，不得判定通过
- `docs/11_test/e2e_report.md` 包含版本、环境、证据、缺陷、重测、风险及明确 PASS/FAIL 结论；失败则回到责任 Stage，修复后用新候选版本重跑受影响范围

### Gate 4：Release Readiness（单人协议）

按 0.4 节五步协议执行，AI 复审使用**发布经理角色**（附录 B.6），且只能审查 Gate 3 = `APPROVED` 且 Stage 17 = `PASS` 的同一候选 commit/制品。`docs/12_deployment/gate4_review.md` 必须记录：候选版本与制品校验值、Gate 3/E2E 证据、配置与密钥项完整性（仅记录是否就绪，不记录值）、数据库迁移与兼容性、备份/恢复及回滚方案、监控/告警/值守方案、遗留风险的责任人与期限、发布窗口，以及明确结论。方案中的命令、阈值、RPO/RTO、责任人和 Stage 18 实演步骤必须可判定，不接受“上线时再看”。

## Stage 18：CI/CD 与部署

### 个人执行要点

- 时间盒：0.5~1 天
- 个人版目标：**一条命令能部署，一条命令能回滚，出事了有人（监控）告诉你**——做到这三点即达标

### 提示词

```text

【启动协议——先核验，后修改】

7. 数据保护：明确备份频率、保留期、加密、RPO/RTO；至少完成一次隔离环境
   恢复演练并记录耗时、校验结果和证据
8. 回滚：提供应用一键回滚命令、触发条件、目标版本和验证步骤；数据库变更
   优先采用向后兼容的 expand/contract，无法逆迁移时提供经验证的补偿/前滚方案
9. 发布清单：覆盖发布前基线、发布中观察、发布后冒烟、告警确认、回滚决策点、
   负责人和时间戳

【执行边界与失败处理】
- 默认先在测试/预生产环境执行；生产部署必须同时满足 Gate 4 APPROVED（GO）、目标版本一致、
  人工确认。未获确认时只交付配置、dry-run 和操作步骤
- 任一质量检查、构建、迁移、readiness 或发布后冒烟失败，立即停止晋级；
  达到回滚触发条件时按预案回滚，不在生产环境临场试错
- 保留失败命令、退出码、平台事件和日志摘要；同一路径连续失败 2 次后停止，
  输出已尝试动作和下一步最小建议
- 工具、权限或平台不可用时标 [BLOCKED]/[NOT RUN]；不得将 dry-run 当作真实部署，
  不得声称未执行的回滚、恢复或告警测试已通过

【完成定义（DoD）】
- [ ] Gate 4 APPROVED（GO）的同一制品可用一条已记录命令部署，版本/checksum 可核对
- [ ] 在测试/预生产环境完成从零部署和发布后冒烟，必需检查 100% 通过
- [ ] 一键回滚在测试/预生产环境实演成功，恢复到目标版本且数据校验通过
- [ ] 数据备份与恢复实演成功，实际 RPO/RTO 结果已记录
- [ ] liveness/readiness、日志、错误追踪及关键指标可见，测试告警真实触达责任人
- [ ] pipeline 与运行权限符合最小权限，仓库/日志/制品 secret 告警 = 0

【最终输出——固定格式】
1. 结论：DONE / PARTIAL / BLOCKED；实际执行到哪个环境
2. 变更文件与 diff 摘要；pipeline 各阶段、权限和失败条件
3. 制品身份：版本、commit SHA、checksum、目标环境
4. 验证证据：完整命令、退出码、运行链接/日志摘要、健康与冒烟结果
5. 部署/迁移/回滚/恢复演练：步骤、耗时、结果与证据
6. 可观测性：指标、阈值、告警测试、通知结果和 runbook
7. 未执行项、已知限制、剩余风险、负责人/期限与再次执行方式
8. 自检：逐条回应 DoD；未知项标 [UNKNOWN]，未执行项标 [NOT RUN]
```

### 质量门禁

- 发布制品与 Gate 4 APPROVED（GO）记录的 commit SHA/checksum 一致；环境间使用同一不可变制品
- 测试/预生产环境从零部署与发布后核心冒烟通过率 100%；部署和回滚命令及退出码可复现
- 回滚演练在目标时限内成功，应用版本、健康状态与数据一致性校验全部通过；数据库无可逆路径时已有验证过的补偿/前滚方案
- 备份恢复演练通过，数据校验正确，实测 RPO/RTO 不超过冻结目标；无冻结目标则 Gate 4 不得判 APPROVED（GO）
- liveness/readiness、结构化日志、错误追踪和关键指标可用；关键测试告警触达率 100%，均有关联责任人和 runbook
- pipeline 最小权限与生产人工确认有效；严重/高危镜像或依赖问题 = 0，secret 告警 = 0
- `cicd_pipeline_spec.md` 与 `release_checklist.md` 包含版本、命令、证据、停止/回滚条件、风险和责任人；任一必需实演为 `[NOT RUN]` 时不得宣称交付完成

# 附录 B：AI 虚拟团队提示词集

> 使用纪律：**每次评审都在全新会话中运行**；输入仅限“冻结资产 + 待评审产出物 + 必要的验证证据”，单次会话遵守“文档 ≤5 份、长文只给相关章节”。不要向评审 AI 解释提交者意图，也不要要求它直接修改产出物。

> 复制任一模板时，必须保留 0.5 节的六类信息：角色与边界、权威输入、任务与输出契约、约束、不确定与冲突处理、证据与完成前自检。最终结果末尾统一追加：①变更/评审摘要；②产出清单及状态；③全部未决与冲突；④证据索引；⑤逐项 Self-Check（Pass/Fail/N/A + 理由）。

# 附录 C：简版变更控制（单人 CCR）

冻结资产要改时，必须先登记 CCR，再修改。**核心目的：阻止“顺手改”——即使是 L1，也不允许先改后补记录。级别按实际影响判定，而不是按改动行数或文件类型判定；拿不准时向上升级。**

| 级别 | 可判定定义 | 必做流程 | 审批 / 冷却 | 退出条件 |
|---|---|---|---|---|
| L1 | 仅文案、注释、拼写、等价重构或视觉微调；不改变 BR/AC、交互行为、权限、契约、Schema、安全、依赖、部署与测试预期 | 登记 → 影响核对 → 修改 → 定向验证 → 归档 | 可自批；无需隔夜 | 验证通过、受影响文档已同步、commit/证据已登记 |
| L2 | 局部且非破坏性设计变化；如单页交互调整、可选 API 字段新增、内部实现变化；可能影响一个或多个下游资产 | 登记 → 影响分析 → 明确方案 → 批准 → 修改 → 同步下游 → 回归验证 | 自批，但必须完成“三问”和回归计划；风险不清则升级 L3 | 影响资产全部更新、定向回归通过、必要 Gate 条目复核完成 |
| L3 | 业务规则、MVP 范围、权限、核心流程、数据语义、破坏性 API/Schema、关键 NFR、安全模型或发布/回滚策略变化 | 登记 → **强制隔夜** → 全链路影响分析 → 明确批准 → 修改 → 全量回归 → 受影响 Gate 复审 | 冷却至少一晚；复审前不得合并/发布 | 受影响 Gate 得到新结论，追溯链与基线版本更新，回归证据齐全 |

CCR 状态只允许：`DRAFT → ASSESSED → APPROVED → IMPLEMENTING → VERIFYING → CLOSED`；不采纳时使用 `REJECTED`，已批准但不再执行时使用 `CANCELLED`。只有 `APPROVED` 才能开始修改；只有退出条件全部满足才能进入 `CLOSED`。

**L2/L3 自问三问：**

1. 这个变更影响哪些上游依据和下游资产？（沿链路核对：BR/NFR → Interaction/Prototype → Architecture/Data/API → PRD/High-fi → AI Context → Code → Test → Deployment）
2. 需要重走或定向复核哪个 Gate？业务/交互行为看 Gate 1；架构/数据/API 看 Gate 2；代码/安全看 Gate 3；发布/回滚看 Gate 4。
3. `AGENTS.md`、可选的 `CLAUDE.md` 适配层、Task Brief、追溯矩阵与回归计划是否需要同步？

**登记格式**（docs/13_changes/change_log.md）：

```markdown
| CCR ID | 日期 | 级别 | 变更摘要 | 冻结基线 | 决策 | 负责人 | 状态 | 详情链接 |

```

每个 L2/L3（L1 可在 `change_log.md` 同行补齐）至少记录以下字段：

```markdown
CCR ID：CCR-xxx
状态：DRAFT / ASSESSED / APPROVED / IMPLEMENTING / VERIFYING / CLOSED
提出日期：YYYY-MM-DD
冻结基线：{commit SHA / tag / 文档版本}
```

# 附录 F：防幻觉标记速查

正文中的 `[TBD-*]`、`[CONFLICT]` 等写法是类别简称；创建实际条目时必须带三位流水号，例如 `[TBD-BIZ-001]`、`[CONFLICT-002]`。同一问题跨文档沿用同一编号，不得通过新编号规避未关闭项。

允许在规则模板中使用的类别简称仅限：`[TBD-RESEARCH]`、`[TBD-BIZ]`、`[TBD-UX]`、`[TBD-ARCH]`、`[TBD-PRD]`、`[TBD-FE]`、`[TBD-BE]`、`[TBD-INFRA]`、`[TBD-TOOLING]`、`[MISSING-SOURCE]`、`[CONFLICT]`、`[ASSUMPTION]`、`[DERIVED]`、`[DERIVED-VISUAL]`。实际登记时一律使用带编号形式。

| 标记类别 | 使用场景 | 必填信息 | 允许的下一步 | 关闭证据 |
|---|---|---|---|---|
| `[TBD-RESEARCH-nnn]` | 市场、用户、竞品、价格、法规或外部事实无法核验 | 主张、来源缺口、影响、验证方法、负责人、期限 | 继续不依赖该事实的分析；不得填“看起来合理”的结论 | 原始/权威来源与核验日期，或删除受影响主张 |
| `[TBD-BIZ-nnn]` | 业务目标、范围、BR、NFR、权限或优先级未确认 | 问题、影响项、候选选项、负责人、期限 | 暂停受影响决策；由产品负责人确认 | 已批准的 BR/NFR/权限条款或 CCR |
| `[TBD-UX-nnn]` | 页面、流程、状态、文案行为或可用性规则未确认 | PG/流程节点、缺口、影响、负责人、期限 | 回到 Stage 6/7 验证，不在代码中发明 | 更新后的交互资产 / Prototype Review |
| `[TBD-ARCH-nnn]` | 架构边界、NFR 承载、数据语义或 API Contract 待确认 | NFR/API/实体、方案选项、影响、负责人、期限 | 回到 Stage 8-11；实现阶段停止受影响修改 | 更新后的冻结架构/数据/API 资产与 Gate 2 复核 |
| `[TBD-PRD-nnn]` | AC、PRD 状态或页面映射尚未 Ready | AC/PG/状态、来源缺口、影响、负责人、期限 | 只保留映射草案；不得判 Ready for Design/Implementation | Ready 状态 PRD 条款与对应映射 |
| `[TBD-FE-nnn]` | 前端实现、浏览器行为或 Design Token 使用方式待确认 | 文件/组件、复现条件、影响、负责人、期限 | 做最小调查或 PoC；不得改变业务语义 | 代码/官方资料/测试证据与评审记录 |
| `[TBD-BE-nnn]` | 后端实现、数据行为、API 处理方式待确认 | API/实体、场景、影响、负责人、期限 | 对照架构与契约调查；不得新增规则 | 冻结设计条款、代码/测试与评审记录 |
| `[TBD-INFRA-nnn]` | 环境、凭证、部署、监控或运行条件待确认 | 环境、配置键、风险、负责人、期限 | 由基础设施验证；不得猜测真实值 | 配置清单、演练/监控报告（不得含密钥） |
| `[TBD-TOOLING-nnn]` | 工具、运行器、导入机制、命令或版本能力尚未核验 | 工具与版本、待核验能力、官方来源、影响、负责人、期限 | 查阅当前官方文档或执行安全探测；不得把候选能力写成已支持 | 官方文档版本/访问日期或可复现命令结果 |
| `[MISSING-SOURCE-nnn]` | 声称存在的文件、章节、链接、Figma 资产或外部来源不可访问/不存在 | 预期来源、查找位置、受影响结论、负责人、期限 | 将受影响产物置为 Blocked；请求或恢复来源 | 来源可访问且版本固定，或正式批准删除该依赖 |
| `[CONFLICT-nnn]` | 两个或以上权威资产给出不兼容要求 | 冲突双方的路径#章节、影响范围、建议归属阶段、负责人 | 立即停止受影响工作，走 CCR / 回到归属阶段 | 决策记录、更新后的资产版本及必要 Gate 复核 |
| `[ASSUMPTION-nnn]` | 为继续分析而暂用、尚未证实的可逆假设 | 假设、依据、影响、验证方法、负责人、期限 | 仅用于分析/原型；不得作为冻结需求或通过证据 | 来源、实验/测试结果，或批准的风险接受记录 |
| `[DERIVED-nnn]` | 可由已批准输入按明确规则复算的一般推导 | 输入证据、推导规则/公式、结果、复算方法 | 可用于下游，但不得越过权威边界或掩盖缺失输入 | 独立复算结果与全部输入定位 |
| `[DERIVED-VISUAL-nnn]` | 不改变行为/语义、可由冻结 Token 与组件规范推出的纯视觉选择 | Token、组件/variant、映射规则、影响画板 | 可用于高保真；一旦改变行为、字段或状态即改记 TBD/CONFLICT | Token/组件引用与 Figma 节点走查证据 |

`[BLOCKED]`、`[UNKNOWN]`、`[NOT RUN]` 是执行结果，不是问题类别：`[BLOCKED]` 表示当前工作因已登记问题无法继续；`[UNKNOWN]` 表示尚无足够证据作出判断；`[NOT RUN]` 表示检查未执行。三者都不得等同于 PASS；必须关联一个上述编号、补证动作、负责人和期限。

统一记录格式如下，并在当前阶段的跟踪清单登记：

```markdown
| ID | 类别 | 提出位置 | 待确认问题/假设 | 影响资产 | Blocking? | 负责人 | 最晚关闭阶段/日期 | 验证/裁决方法 | 状态 | 关闭证据 |
|---|---|---|---|---|---|---|---|---|---|---|
| TBD-BIZ-001 | TBD-BIZ | 文件#章节 |  |  | Yes/No | 本人 | Gate 1 / YYYY-MM-DD |  | OPEN |  |
```

状态只允许 `OPEN / IN_REVIEW / RESOLVED / ACCEPTED_RISK / CANCELLED`。`RESOLVED` 必须有来源或决策证据；`ACCEPTED_RISK` 必须记录影响、理由、负责人和复查日期，且不得用于关闭 `[CONFLICT-*]`、`[MISSING-SOURCE-*]`、安全红线或契约阻塞项。

规则：外部事实必须记录来源标题、URL/文件、发布日期（如有）与访问日期；引用数字必须能回到原始口径。推测必须标记，不为“文档完整”编造内容，不得用不存在的依赖、API、字段、配置或测试结果填空。进入 Gate 或把 Task Brief 置为 READY 前，所有影响范围、权限、安全、契约或核心流程的 `[CONFLICT-*]`、`[MISSING-SOURCE-*]` 与 Blocking 项必须为 `RESOLVED`；其余未关闭项必须有负责人、期限和明确处置。**标记不是免责说明，而是必须闭环的工作项。**

# 最终原则

```text
调研（AI 主力，你验证，魔鬼代言人挑战）
   ↓
业务建模（BR + 量化 NFR + 狠心砍范围）
   ↓
交互设计 → Prototype
   ↓
★ Gate 1：冷却期 + 换帽 + AI 产品负责人复审
   ↓
工程四件套（选你能独立运维的最简方案）
   ↓
★ Gate 2：AI 架构评审员复审
   ↓
PRD（AC 不可省）∥ 高保真（Figma Design + Tokens，继承 Prototype 行为、不继承 Make 皮肤）
   ↓
AGENTS.md（≤300 行，唯一工程规则权威）+ CLAUDE.md 适配层（如适用，≤60 行）
   ↓
实现（Task Brief + 一个模块一个会话 + 小步提交）
   ↓
★ Gate 3：CI 机器评审 + 隔夜换帽自评 + AI 安全复审
   ↓
E2E（AI 扮 QA 专测你想不到的路径）+ 追溯矩阵
   ↓
★ Gate 4：AI 发布经理保守把关
   ↓
部署（一键部署 / 一键回滚 / 出事有人喊）
   ↓
反馈 → 简版 CCR（L3 强制隔夜）→ 回到对应阶段
```

> **企业流程的本质不是"人多"，而是"决策有依据、变更有痕迹、质量有第三方"。单人开发用三样东西补齐：冷却期替代"别人的时间"，AI 虚拟团队替代"别人的视角"，Checklist 机械执行替代"别人的责任心"。流程一步不省，只是每一步都轻到你愿意做。**
