# 企业研发 AI 助手 — 产品调研与设计

本文件夹汇集「Enterprise AI Developer Assistant」从原始思路到市场、竞品、架构与路线图的决策材料，供产品负责人与研发负责人评审立项使用。

---

## 产品一句话定位

面向异构研发工具链（Jira / Confluence / GitHub / Jenkins）的企业团队，提供**生而受治理**的 AI 工作流编排层——把测试编排、发布管理、跨系统信息流转做到「AI 干活、人做决策」，而不是又一个 Coding Agent。

---

## 核心原则摘要（5 条）

来源：[00-原始项目思路.md](./00-原始项目思路.md) 第十节。

1. **AI 是编排者，不替代 Jenkins** — 正式测试永远跑在 Jenkins；AI 只做 Trigger / Polling / Summary / 回写。
2. **Docker 是工具，不是平台** — Sandbox 按需用于脚本与数据分析，不承载正式测试。
3. **Workflow 比 Chat 更重要** — 固定业务页面 + AI 对话框；结构化流程优先于纯对话。
4. **Connector、Workflow、Memory、Skills 是核心资产** — 长期可复用、可治理、可迁移。
5. **LLM 可替换，不绑定单一厂商** — 自研轻量 Runtime + 统一 Model Adapter；**不绑定 Claude Agent SDK**。

补充硬约束：邮件**仅生成草稿、不发送**；数据库全表预留 `tenant_id`（当前单企业）。

## 「需要确认」清单与建议决策

来源：原始思路第九节；架构文档第十章给出详细论证。下表为决策摘要（标注「建议」）。

| # | 待确认项 | 建议决策 |
| --- | --- | --- |
| 1 | Workflow Builder 是否进入 V1？ | **建议：不进 V1。** V1 用工程侧 YAML 声明式 Workflow；前端只读进度可视化。Builder 放长期（12 月+）。 |
| 2 | Memory 自动保存策略 | **建议：AI 提议 + 用户确认为主。** 仅 User 层低风险偏好可自动保存（可撤销）；Project / Knowledge 一律需确认。 |
| 3 | Connector SDK 规范 | **建议：以 `BaseConnector` + `ToolSpec` 为 SDK 核心**（读写级别、Schema、错误分类、health_check、独立包注册）。中期固化规范，长期扩 Connector。 |
| 4 | Docker 生命周期（持久或临时） | **建议：临时——会话级容器 + 预热池。** 会话内复用、结束销毁；产物拷出对象存储。禁止长期持久容器。 |
| 5 | Release Template 配置方式 | **建议：平台内模板管理，Markdown + YAML front-matter，版本化。** 支持按项目覆盖；可从 Confluence 导入初始化。 |
| 6 | Jenkins Job 标准接口 | **建议：定义「AI 可调 Job 契约」**（`ai-enabled` 标签；统一入参 `PACKAGE_URL`/`TRACE_ID` 等；JUnit 必选；V1 轮询 REST，预留 webhook）。 |

## 下一步行动建议（产品 / 研发负责人）

1. **本周内拍板「需要确认」6 项**（至少拍板 1、2、4、6；5 可与 Release 试点团队共定）。未拍板项不要阻塞 MVP，但需写入 ADR。
2. **立项口径对齐**：对内汇报用「Agentic SDLC 编排 / AI Native Developer Portal」，避免自称 Coding 工具；ROI 锚定测试整理耗时、Release 准备周期、回写准确率。
3. **研发启动顺序（见 04）**：MVP 只打「自动化测试中心」闭环；S1 第一天申请 Jenkins / Jira / Confluence / SSO 联调账号。
4. **用 02 竞品结论支撑立项**：差异化叙事锚定「异构工具链 + Jenkins 存量 + 人审治理」，避免与 Coding Agent 红海对撞。
5. **治理显性化**：把「邮件只草稿、正式测试只 Jenkins、回写必人审」写进演示脚本与审计页面，作为信任卖点而非限制说明。
