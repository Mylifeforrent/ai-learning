# 开发路线图与技术栈设计

> Enterprise AI Developer Assistant（企业研发 AI 助手）
> 依据 [00-原始项目思路.md](./00-原始项目思路.md) 制定 | 技术栈版本核实时点：2026 年 7 月
> 关联：[README.md](./README.md) · [03-架构设计.md](./03-架构设计.md)（V1 目标态；本文为到达路径）· [01-市场调研.md](./01-市场调研.md) · [02-竞品分析.md](./02-竞品分析.md)
> 团队产能假设：2-5 人小团队，排期按 2 周 / Sprint

---

## 0. 规划总原则

所有排期与选型决策服从原始思路中已定的核心原则：

1. **AI 是编排者，不替代 Jenkins**——正式测试永远跑在 Jenkins，AI 只做 Trigger / Polling / Summary。
2. **Workflow 比 Chat 更重要**——排期上优先打通一条完整业务闭环，而不是先把 Chat 做花哨。
3. **Connector、Workflow、Memory、Skills 是核心资产**——这四类代码从第一天起就按"长期资产"的标准设计接口，其余（UI、报表样式等）允许快糙。
4. **LLM 可替换**——所有模型调用必须经过统一 Adapter（LiteLLM 思路），业务代码不出现任何厂商 SDK；**不绑定 Claude Agent SDK**。
5. **Docker 是工具，不是平台**——Sandbox 不进 MVP 关键路径，作为普通 Tool 在短期阶段补充；正式测试永不进 Sandbox。
6. **邮件仅草稿**——系统不实现 / 不注册发送能力；`tenant_id` 全表预留。

小团队的三条排期铁律：

- 每个 Sprint 必须产出**可演示**的东西，不做纯"打地基" Sprint。
- 依赖外部系统（Jenkins / Jira / SSO）的联调工作**前置**，这是企业内项目最大的隐性延期来源。
- 能用 Postgres 解决的不引入新中间件（队列、缓存、向量库首选都在 Postgres 内解决；与 [03](./03-架构设计.md) 一致：Redis 仅多实例时可选引入）。

### 阶段总览（必须清晰区分）

| 阶段 | 时间窗 | 目标一句话 | 相对目标态（03） |
| --- | --- | --- | --- |
| **MVP** | 0–3 月 | 打通自动化测试中心闭环，证明 ROI | Runtime v0 + 核心 Connector；无 Sandbox / 无 Workflow Engine |
| **短期** | 3–6 月 | Skills / Memory / Sandbox / 审计到位 | 接近日常助手 + 测试中心的完整能力 |

| **长期** | 12 月+ | AI Native Developer Portal | Builder / RAG / 多租户 / Marketplace |

## 1. MVP 阶段（第 0–3 个月）

> 与 [03](./03-架构设计.md) 的关系：本阶段只落地「测试中心闭环 + Runtime v0 + 核心 Connector」，不追求架构图全量能力。

### 1.1 MVP 范围裁剪

**选定的闭环：自动化测试中心**。三大功能中，它是唯一"输入输出都可客观度量"的场景：测试报告好不好一目了然，节省的人工时间可直接量化，最适合用来验证产品价值、争取内部支持。相比之下，日常开发助手与通用 Chat 产品同质化严重，难以证明"为什么不直接用 Cursor / Copilot"；Release Assistant 依赖企业内部合规检查接口和 Release Template 规范（原始思路"需要确认"清单第 5、6 条尚未落定），不确定性最高，放到**中期（6–12 月）**。

| V1 功能 | MVP 保留 | MVP 砍掉 | 理由 |
|---|---|---|---|
| 日常开发助手 | 基础 Chat（流式）、会话历史、内置 3-5 个官方 Skills、Markdown 导出 | 用户自建 Skills、Skills 分享与审核、完整三层 Memory | Chat 是所有功能的载体必须有；但 Skills 生态没有种子用户时是空市场，先由官方内置 Skills 验证格式设计 |
| 自动化测试中心 | **完整闭环**：上传测试包 → 触发 Jenkins Job → 轮询结果 → AI 汇总美化 → 用户审核 → 更新 Jira/Confluence → 证据沉淀 | 多 Jenkins 实例、复杂报告模板自定义 | 这是 MVP 的主闭环，一步不裁 |
| Release Assistant | 无 | 全部 | 依赖未确认的企业内部接口；测试中心先把 Jira/Confluence Connector 建好，**中期（6–12 月）**做 Release Assistant 时可复用，边际成本低 |
| Memory | 两层简化版：会话历史（自动）+ 项目 Memory（用户手动保存，Markdown + Postgres 元数据） | User Memory 自动沉淀、Knowledge 层、自动保存策略 | 自动保存策略未确认（"需要确认"第 2 条）；手动保存先验证存储格式和导出迁移能力 |
| Docker Sandbox | 无 | 全部 | 原则"Docker 是工具不是平台"，MVP 闭环不依赖它 |
| 认证 | SSO（OIDC）+ 账密 fallback | 细粒度 RBAC | 企业内上线的硬门槛，必须有；角色先只分 普通用户 / 管理员 两级 |

数据库 schema 从第一天预留 `tenant_id`（默认单租户常量），避免未来全表迁移。

### 1.2 MVP 技术栈清单

版本策略：**选 LTS / 长支持线，锁定大版本，小版本随安全更新滚动**。以下版本已按 2026 年 7 月现状核实。

| 层 | 选型 | 版本 | 说明 |
|---|---|---|---|
| 前端框架 | Next.js（App Router）+ React | Next.js 16（Active LTS，16.2.x）+ React 19 | Next.js 16 为当前 LTS 线，安全支持至 2028；15.x 维护期 2026-10 结束，不选 |
| 前端样式/组件 | TailwindCSS + shadcn/ui | Tailwind 4.x（4.3+） | shadcn/ui 源码引入，方便定制企业 UI |
| 前端语言/工具 | TypeScript、TanStack Query | TS 5.x | 服务端状态统一走 TanStack Query；Chat 流式用 SSE（原生 `fetch` + ReadableStream） |
| 后端框架 | FastAPI + Uvicorn | FastAPI 0.136+（Python 3.13） | Python 3.13 生态兼容性最稳；Pydantic v2（2.13+）做全部 schema 校验 |
| ORM / 迁移 | SQLAlchemy 2.0（async）+ Alembic | SQLAlchemy 2.0.x | 从第一张表开始就走 Alembic 迁移 |
| 数据库 | PostgreSQL | 18.x | 2025-09 GA 的当前主线，支持到 2030；一库多用：业务数据、任务队列（`SELECT ... FOR UPDATE SKIP LOCKED`）、后续 pgvector |
| LLM Adapter | LiteLLM（Python SDK / Router 模式） | 1.86+ | 统一接 Claude / GPT / Gemini / Qwen / DeepSeek；MVP 内嵌 SDK 即可，短期阶段再评估独立 Proxy 模式 |
| Agent Runtime | **自研轻量 Runtime** | — | MVP 只实现三件事：Tool Calling 循环（Planner 先用"模型原生 tool use"，不自研规划算法）、Tool Router（带权限声明）、结构化输出校验（Pydantic）。Workflow Engine 不在 MVP 自研范围 |
| 任务执行 | Postgres 任务表 + asyncio worker | — | Jenkins 轮询、报告生成等异步任务用数据库队列，不引入 Redis/Celery，部署只有 App + Postgres 两个组件 |
| Connector | Jira / Confluence（REST）、Jenkins（REST + Job 参数化） | 官方 REST API | 自封装薄客户端（httpx），统一鉴权、重试、审计埋点；这层是未来 Connector SDK 的雏形 |
| 认证 | OIDC（Authlib）对接企业 SSO；账密 fallback | Authlib 1.x | 会话用 HttpOnly Cookie + 服务端 session |
| LLM 可观测 | Langfuse（self-host） | Server v3.x + Python SDK v4.x | 从 MVP 第一天接入，trace 每次 LLM 调用的 prompt/token/延迟/成本 |
| 部署 | Docker Compose（企业内网单机） | Docker Engine 27+，docker-py 7.2（短期阶段 Sandbox 用） | MVP 不上 K8s |
| CI | GitHub Actions（或企业内 GitLab CI/Jenkins） | — | lint（ruff / eslint）+ 单测 + 镜像构建 |

### 1.3 里程碑拆解（6 个 Sprint）

假设 MVP 期投入 2-3 人（1 全栈偏前端、1-2 后端）。

| Sprint | 主题 | 交付物 |
|---|---|---|
| S1（第 1-2 周） | 骨架 + 认证 + 打通模型 | Monorepo 脚手架；SSO 登录可用；基础 Chat 页面流式对话跑通（LiteLLM 接 2 个模型）；Postgres schema v1（含 `tenant_id`）；Langfuse 接入。**同步启动**：向 IT 申请 Jenkins/Jira/Confluence 测试环境与服务账号（最长的外部依赖，第一天就提） |
| S2（第 3-4 周） | Agent Runtime v0 + 只读 Connector | Tool Calling 循环 + Tool Router；Jira / Confluence 只读 Connector（查 issue、读页面）在 Chat 中可用；会话历史持久化 |
| S3（第 5-6 周） | Jenkins 打通 | 测试包上传（版本化存储）；Jenkins Connector（参数化触发 + 轮询 + 拉取 JUnit/Allure 结果）；测试任务列表页与详情页 |
| S4（第 7-8 周） | AI 汇总 + 人审 + 回写 | AI 生成测试报告（结构化输出 + 美化 Markdown）；用户审核流（approve / 修改后 approve / reject）；审核通过后更新 Jira 评论与 Confluence 页面（写操作全部过人审，这是 human-in-the-loop 的第一个落点） |
| S5（第 9-10 周） | 证据沉淀 + Memory + 导出 | Release 证据归档（报告、Jenkins 构建号、审批记录关联存储）；项目 Memory 手动保存与引用；会话/报告导出 Markdown & JSON；内置官方 Skills 3-5 个（如"生成测试摘要""JQL 查询助手"） |
| S6（第 11-12 周） | 试点 + 打磨 | 邀请 1 个真实团队试点跑真实测试包；修 bug、补审计日志（谁在何时让 AI 写了什么到 Jira）、安全自查（secrets、注入）；MVP 验收评审 |

### 1.4 MVP 验收标准

**功能验收**

- 一名 QA 用户不看文档能独立完成：上传测试包 → 触发 Jenkins → 收到 AI 报告 → 审核 → Jira/Confluence 更新成功 → 在证据库查到本次记录。
- 所有对外部系统的**写操作**（Jira/Confluence）100% 经过用户审核，无旁路。
- 切换 LLM Provider（如 Claude ↔ Qwen）只改配置不改代码，闭环仍可跑通（验证"LLM 可替换"原则）。

**量化指标（试点 2 周内）**

- ≥ 1 个真实团队、≥ 20 次真实 Jenkins Job 通过平台完成闭环。
- 测试结果整理与同步耗时：从人工约 1-2 小时降至 10 分钟以内（含人审）。
- AI 报告首次生成的人审通过率（不需大改直接 approve 或小改后 approve）≥ 80%。
- Langfuse 上可查每次调用的完整 trace，单次闭环 token 成本有数、可解释。

## 2. 短期阶段（第 3–6 个月）

### 2.1 阶段目标

在测试中心闭环已验证的基础上，补齐 **Skills 体系、三层 Memory、Docker Sandbox（工具）、审计**——让日常助手可用、可扩展、可治理。本阶段**不交付** Release Assistant 与 Workflow Engine（放入中期），避免并行战线过宽。

### 2.2 排期（Sprint 7–12）

| 时间 | 主题 | 内容 |
|---|---|---|
| M4（S7–S8） | Skills 体系 v1 | 落定 Skill 包格式（`skill.yaml` + prompt.md + 可选 python/shell + permissions/timeout/sandbox，参考 Hermes）；加载器与执行器；个人 Skill 创建即用；官方 Skills 迁移到该格式 |
| M4–M5（S8–S10） | Docker Sandbox 工具 | 与 [03 §五](./03-架构设计.md) 对齐：**会话级临时容器 + 预热池**（非持久；非「平台」）。首版可先实现「出池即用 / 会话绑定 / 空闲销毁」，资源硬限制（CPU/内存/超时/默认无网络）；作为 Runtime Tool 暴露 Python / Shell / Excel / XML / 日志 / 统计；Skill 声明 `sandbox: true` 即路由到容器。**正式测试绝不在此执行** |
| M5–M6（S10–S12） | Skills 治理 + Memory 三层 + 审计 | 团队 Skill：提交 → 管理员审核 → 发布（版本与回滚）；Memory 补齐 User / Project / Knowledge，自动保存策略按建议落地（AI 提议 + 用户确认）；统一审计日志（外部写操作、Skill、Sandbox） |

### 2.3 本阶段技术栈差异（相对 MVP）

| 组件 | 选型 | 相对 MVP 的变化 |
|---|---|---|
| Skills | Hermes 风格包 + 审核状态机 | MVP 仅内置 Skills → 用户可自建 / 团队共享 |
| Sandbox | docker-py 7.2 + 预热池 | **新增**；MVP 无 Sandbox |
| Memory | 三层 + draft/confirm | MVP 两层手动 → 完整三层与策略 |
| 对象存储 | MinIO / S3 兼容 | Skill 包、Sandbox 产物从库内迁出 |
| 审计 | Postgres 追加写表（可按月分区） | MVP 基础埋点 → 可查询管理后台 |
| 队列 | 仍默认 Postgres | 不引入 Redis（除非已多实例） |
| Workflow Engine | **不上** | 测试中心流程仍可代码编排，中期再提炼 |

### 2.4 短期验收要点

- 个人 Skill 可创建即用；团队 Skill 经管理员审核后全员可见，权限声明在运行时强制生效。
- Sandbox 执行 Python/日志分析成功，超时/无网络限制生效；会话结束容器销毁，产物可在对象存储找回。
- Memory 三层可读写导出；无「静默写入 Project/Knowledge」。
- 审计后台可按用户 / 工具 / trace_id 追溯一次测试回写链路。

## 3. 中期阶段（第 6–12 个月，完成 V1）

### 3.1 阶段目标

交付 **Release Assistant**，并将测试中心 / Release 提炼为声明式 **Workflow Engine**，完成与 [03](./03-架构设计.md) 对齐的 **V1 发布**。同步固化 Connector SDK 雏形，为长期扩 Connector 铺路。

### 3.2 排期（Sprint 13–24）

| 时间 | 主题 | 内容 |
|---|---|---|
| M7–M9（S13–S18） | Release Assistant | GitHub Connector（PR / commit 只读）；Release Template（Markdown + YAML front-matter，平台内版本化，见「需要确认」建议 #5）；生成 Change Request；对接企业内部合规检查；Release Checklist；邮件**草稿**（不发送）；复用人审 UI 与测试证据关联 |
| M9–M11（S18–S22） | Workflow Engine v1 | 将测试中心、Release 从代码写死流程重构为声明式 YAML（步骤 / 依赖 / 人审 / 重试）；自研引擎（状态机 + Postgres 持久化 + 断点恢复）；RBAC 细化（项目级）；性能与稳定性打磨 |
| M11–M12（S22–S24） | Connector SDK 雏形 + V1 发布 | 将既有 Connector 收敛到统一 `BaseConnector` / `ToolSpec` 规范（回答「需要确认」#3）；V1 验收、文档与试点扩面；**V1 正式发布** |

Workflow Engine 放在中期而非 MVP，是刻意的：先用代码把两条真实流程跑到稳定，再提炼引擎。这也回答了「需要确认」#1——**Workflow Builder（可视化）不进 V1**，但 **Workflow Engine（执行层）进 V1 收尾**。

### 3.3 本阶段技术栈差异（相对短期）

| 组件 | 选型 | 理由 |
|---|---|---|
| Workflow Engine | **自研**：YAML + 状态机 + Postgres | 不引入 Temporal / Airflow；边界：不做分布式调度；超出再评估 |
| GitHub Connector | GitHub App + REST（httpx / PyGithub） | V1 只读；权限最小化 |
| Release / 邮件 | `release_templates` + `email_drafts` | 仅草稿；系统不注册 `mail.send` |
| Connector SDK | `BaseConnector` 包规范 | 与 03 第三章一致；中期末固化 |
| Redis（可选） | Redis 7.x / Valkey | 仅 SSE 多实例 / 限流需要时引入 |
| 观测 | Prometheus + Grafana | 中期起补齐基础层告警（Jenkins 积压、Workflow 卡死等） |

### 3.4 团队配置建议（中期 4–5 人）

| 角色 | 人数 | 职责 |
|---|---|---|
| Tech Lead / 全栈 | 1 | 架构把关、Workflow Engine 与 Runtime 核心、跨团队协调 |
| 后端工程师 | 2 | 一人主攻 Connector + Release；一人主攻 Engine + 审计 / RBAC |
| 前端工程师 | 1 | Release / 审核流 / 管理后台；进度可视化（只读） |
| DevOps / QA（兼职） | 0.5–1 | staging/prod、监控、E2E |

MVP / 短期可由其中 2–3 人先行；需指定试点团队业务接口人作为常驻真实用户。M6 起建议引入第二个试点团队，降低过拟合。

### 3.5 V1 验收（中期末）

- Release：从 Jira + GitHub 生成 CR / Checklist / 邮件草稿，合规检查可跑或人工确认项占位；**无自动发信**。
- 测试中心与 Release 均由同一套 Workflow Engine 驱动，YAML 可版本管理与断点恢复。
- 切换模型 Provider 只改配置；`tenant_id` 仍为单租户常量但 schema 完整。
- 与 03 目标态能力清单对齐（见 03「与路线图的对齐说明」）。

## 4. 长期阶段（第 12 个月+，AI Native Developer Portal）

### 4.1 演进路径与依赖关系

依赖关系（必须先做的在前）：

```
Connector SDK(中期已有) ──► 更多 Connector（GitLab/IM/制品库…）
Workflow Engine v1(中期已有) ──► Engine 强化 ──► Workflow Builder(可视化)
Memory/Knowledge(短期已有) ──► 企业知识库 RAG
Sandbox Docker(短期已有) ──► SandboxBackend 抽象 ──► K8s Job / gVisor / Firecracker
tenant_id 预留(MVP 已有) ──► 多租户隔离/配额 ──► 多 BU 或对外
```

### 4.2 分期计划

| 时间 | 主题 | 内容与技术方向 |
|---|---|---|
| M12–M16 | Engine 强化 + 更多 Connector | 定时 / Webhook 触发、并行步骤、补偿语义、Workflow 版本化；新增 2–3 个高频 Connector 验证 SDK |
| M16–M20 | Workflow Builder + 企业知识库 | **Builder**：React Flow（xyflow），产出物即 Engine YAML（与手写同构）。**RAG**：Postgres + pgvector；embedding 过 LiteLLM；瓶颈后再评估独立向量库 |
| M20–M24 | 多租户 + 可插拔 Sandbox | Postgres RLS；LiteLLM Proxy 的 key/budget；`SandboxBackend` 接口 + K8s Job / gVisor / Firecracker |
| M24+ | Marketplace + 开放 API | Skills/Workflow 市场；端到端研发流程模板；对内开放 API/SDK |

关键取舍：**多租户排在 Workflow Builder 之后**。当前单企业，Builder 先扩大用户面；出现第二租户（对外 / 多 BU）再上多租户。若商业化提前，两项可对调。

### 4.3 长期技术栈差异（相对 V1）

| 能力 | V1（中期末） | 长期增量 |
|---|---|---|
| 流程编排 | YAML + Engine，无可视化 Builder | React Flow Builder |
| 知识 | 三层 Memory | RAG 摄取管道 + 向量检索 |
| 租户 | `tenant_id` 常量 | RLS + 配额 + 凭据隔离 |
| Sandbox | Docker 会话级 + 预热池 | 可插拔 Backend |
| 模型 | LiteLLM SDK / Router | Proxy 模式预算治理 |
| 产品形态 | 三大固定场景 | Marketplace + 开放 API |

## 5. 横切关注点

### 5.1 测试策略

- **单元/集成**：后端 pytest + pytest-asyncio，Connector 用 respx/vcr 录制回放；前端 Vitest + Testing Library；关键闭环 Playwright E2E。
- **LLM 输出评估**：为「测试报告汇总」「Change Request 生成」建立 golden 用例集，CI 中 LLM-as-judge + 规则断言；Langfuse dataset/eval 承载。
- **Sandbox 安全测试**：逃逸、资源耗尽、网络访问负向用例进入 CI（短期起）。

### 5.2 CI/CD

- 主干开发 + 短分支 PR；CI：ruff/mypy/eslint → 单测 → 构建镜像 → E2E（nightly）。
- 部署：MVP 期 Docker Compose 单机；短期起 staging/prod；变更只走 Alembic。
- Prompt 视为代码：同仓库、同评审、同回滚。

### 5.3 可观测性

- **LLM**：Langfuse self-host 从 MVP 第一天接入。
- **应用**：structlog + OpenTelemetry，与 Langfuse 统一 `trace_id`。
- **基础**：Prometheus + Grafana（中期起）；告警含 Jenkins 积压、Workflow 卡死、LLM 错误率/成本突增。

### 5.4 成本控制（token）

- 全量过 LiteLLM；模型分级路由；Prompt 缓存与日志裁剪；MVP 设月度预算与超额熔断；多租户阶段启用 Proxy budget。

### 5.5 安全与合规

- AI 可更新 Jira/Confluence（过人审）；**禁止发邮件**（仅 Draft）——Tool Router 白名单硬约束。
- 凭据信封加密；外部内容按不可信注入；Memory 可导出；写操作全量审计。

### 5.6 主要技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 自研 Runtime / Engine 膨胀 | 排期黑洞 | 严格边界；每季度评审是否引入 Temporal |
| LLM 幻觉 / 格式漂移 | 写脏 Jira | 结构化输出 + 规则断言 + 100% 人审 |
| 企业系统对接延期 | MVP 阻塞 | S1 第一天提权限申请；Connector 先只读 |
| 试点过拟合 | 泛化差 | 模板配置化；中期引入第二试点团队 |
| 开源依赖 breaking change | 升级成本 | 锁版本 + Adapter 再包一层 |
| Sandbox 逃逸 | 安全事故 | 无网络默认、硬限制、会话销毁；长期升 gVisor/Firecracker |
| 关键人依赖 | 单点 | ADR + 结对轮换 |
