# PPT Agent 设计思路与技术落地方案

来源页面：https://linux.do/t/topic/1782304

整理日期：2026-06-11

## 1. 核心结论

这篇帖子分享的 PPT Agent 不是传统的“输入主题 -> 生成大纲 -> 套模板”路线，而是把专业 PPT 团队的工作流拆成一条 Agent 化流水线：

```text
主题输入
  -> 需求调研
  -> 资料检索
  -> 结构大纲
  -> 页面策划稿
  -> 视觉设计稿
  -> SVG / PPT 可编辑资产
```

它的关键判断是：PPT 的质量主要由内容策略、结构逻辑、页面策划和视觉表达共同决定。Agent 不应该直接“画页面”，而应该先像顾问、策划师、信息架构师、设计师一样逐层工作。

对你自研 PPT Agent 来说，可以把它理解为一个多阶段内容生产系统，而不是一个单 Prompt 生成器。

## 2. 原文方法论拆解

### 2.1 从提问开始，而不是从生成开始

原文反对“一键生成”的主要原因是：主题本身通常不足以产生高质量 PPT。真正做 PPT 前，需要先确认：

- 给谁看：受众是谁，知识水平、职位、关注点是什么。
- 为什么做：汇报、融资、培训、销售、发布会、复盘、方案评审等目标不同，结构完全不同。
- 要达成什么：说服、解释、展示成果、推动决策、传递品牌印象。
- 可用材料有哪些：是否有公司资料、数据、官网、竞品、年报、产品文档、客户案例。
- 风格约束是什么：商务、科技、咨询、极简、发布会、企业品牌规范等。

工程上，这意味着第一个 Agent 应该是“需求澄清 Agent”，负责读取主题、做初步检索，然后向用户提出少量关键问题。只有当需求足够明确，才进入大纲阶段。

### 2.2 大纲采用“数字便利贴”思路

原文提到将复杂 PPT 拆成一页页“数字便利贴”。这个思路本质上是把 PPT 的结构从线性文本转成可编辑的页面卡片：

- 每张便利贴对应一页幻灯片。
- 每页只承载一个核心观点。
- 用户可以拖拽、增删、重排、合并、拆分。
- Agent 可以对每页进行独立补充、改写和设计。

这个设计对产品很重要，因为它让用户在视觉设计前就能把内容结构看清楚。自研时建议把“页面卡片”作为核心中间态，而不是只保存一段 Markdown 大纲。

### 2.3 大量检索资料，让内容有事实基础

原文强调“大纲只是骨架，血肉来自真实资料”。它的实现可以分两层：

- 主题级检索：了解行业背景、市场现状、公司信息、产品信息、竞品、趋势。
- 页面级检索：按每页标题或要点继续检索，补齐数据、案例、论据和图表素材。

这一步的产物不应该直接塞给设计模型，而应该沉淀为结构化资料库，供后续大纲、策划稿、页面文案和图表生成复用。

### 2.4 加入“策划稿”阶段

原文最有价值的设计点之一，是在视觉设计前增加“策划稿”。策划稿不是最终 PPT，也不是纯文字大纲，而是每页的低保真页面方案：

- 页面要表达什么核心观点。
- 页面分成几个信息区块。
- 每个区块放标题、正文、数据、图表、图片还是图标。
- 哪个内容是视觉焦点，哪个是辅助说明。
- 用什么版式承载：对比、流程、时间线、矩阵、列表、卡片、数据看板等。

这相当于把“内容策划”和“视觉设计”解耦。AI 先规划页面，再渲染页面，能显著降低直接生成设计稿时的跑偏概率。

### 2.5 用 Bento Grid / 卡片式布局降低设计难度

原文推荐卡片式布局，本质上是因为它同时满足三点：

- 信息承载力强：一页可以容纳多块内容。
- 变化足够多：卡片大小、位置、数量可以灵活组合。
- 模型容易理解：卡片、网格、层级、留白都可以被明确描述。

这对 AI 生成非常友好。自研时可以将 Bento Grid 作为默认布局引擎，让模型先输出结构化布局 JSON，再由渲染器生成 SVG、HTML 或 PPTX。

### 2.6 生成整页 SVG，而不是纯图片

原文选择整页 SVG 作为设计稿输出，理由是：

- 可导入 Office 2016 及以上版本。
- 可以保持矢量清晰度。
- 在 PPT 和设计软件中有较好的兼容性。
- 相比图片，后续可编辑性更强。

代价是 SVG 工程复杂度高，需要处理文本换行、字体、图标、图表、遮罩、渐变、导入兼容性、元素分组、坐标系统等细节。

如果你的目标是个人使用或快速验证，HTML 渲染会更容易；如果目标是商业可编辑 PPT，SVG 或 PPTX 原生对象更值得投入。

## 3. 推荐系统架构

### 3.1 模块分层

```text
User Interface
  - 需求问答
  - 便利贴大纲编辑
  - 策划稿预览与修改
  - 设计稿预览
  - 导出与编辑

Agent Orchestrator
  - 状态机
  - 任务队列
  - 模型调用
  - 工具调用
  - 失败重试

Domain Agents
  - 需求澄清 Agent
  - 资料检索 Agent
  - 大纲架构 Agent
  - 页面策划 Agent
  - 文案精修 Agent
  - 视觉设计 Agent
  - 质量检查 Agent

Data Layer
  - 项目状态
  - 检索资料
  - 页面卡片
  - 策划稿
  - 设计稿 SVG / HTML
  - 导出文件

Render Layer
  - SVG 生成
  - HTML 预览
  - PPTX 导出
  - 图片/图标资源处理
```

### 3.2 推荐技术栈

最小可用版本：

- 前端：Next.js / React，用于需求问答、便利贴编辑、页面预览。
- 后端：FastAPI / Node.js API，用于编排 Agent 和存储状态。
- 数据库：PostgreSQL，保存项目、页面、资料、生成版本。
- 对象存储：保存 SVG、截图、PPTX、素材图片。
- 搜索：Tavily、SerpAPI、Bing Search API、Exa、Grok 或国内搜索 API。
- 模型：强推理模型负责结构和策划，快模型负责批量页面草稿，视觉/代码能力强的模型负责 SVG。
- 渲染：SVG 作为主输出，HTML 作为预览和调试层，PPTXGenJS / python-pptx 用于导出。

商业增强版本：

- 引入队列：BullMQ / Celery / Temporal，处理多页并发生成。
- 引入版本管理：每页保留 outline、plan、design 的历史版本。
- 引入规则引擎：品牌色、字体、图标库、版式约束、禁用词、合规检查。
- 引入评估系统：自动检测溢出、错字、事实引用缺失、视觉层级不足。

## 5. Agent 工作流设计

### 5.1 需求澄清 Agent

输入：

- 用户主题。
- 用户上传材料。
- 初步网络检索摘要。

输出：

- 用户需求画像。
- 3 到 6 个关键澄清问题。
- 初始约束：页数、风格、受众、目标、交付格式。

实现要点：

- 不要问太多问题，优先问会改变 PPT 结构的问题。
- 可以提供默认假设，减少用户输入压力。
- 用户不回答时，允许 Agent 基于常见场景继续生成，但要标记假设。

### 5.2 资料检索 Agent

输入：

- 项目主题。
- 受众和目标。
- 大纲或页面标题。

输出：

- 结构化资料库。
- 每条资料的来源、摘要、可信度、适用页面。
- 可引用的事实、数据、案例、图表素材建议。

实现要点：

- 先主题级检索，再页面级检索。
- 每页至少绑定 1 到 3 条资料证据，避免空泛生成。
- 对时效性强的主题要记录检索日期。
- 对争议信息要标记不确定性。

### 5.3 大纲架构 Agent

输入：

- 已澄清需求。
- 背景资料摘要。
- 页数要求。

输出：

- 封面、目录、章节、页面卡片、结尾页。
- 每页的核心观点，而不是只有标题。

实现要点：

- 使用金字塔原理：结论先行、上下层归纳一致、同层归类清晰、顺序递进。
- 输出必须是 JSON，便于 UI 编辑和后续 Agent 消费。
- 可以在 JSON 外层使用固定标签包裹，方便从模型输出中提取。

推荐输出契约：

```json
{
  "deck": {
    "cover": {
      "title": "",
      "subtitle": ""
    },
    "sections": [
      {
        "title": "",
        "purpose": "",
        "slides": [
          {
            "title": "",
            "core_message": "",
            "content_intent": "",
            "needed_evidence": []
          }
        ]
      }
    ],
    "closing": {
      "title": "",
      "core_message": ""
    }
  }
}
```

### 5.4 页面策划 Agent

输入：

- 单页 SlideCard。
- 相关资料。
- 品牌和风格约束。

输出：

- 页面策划稿 PagePlan。
- 低保真布局。
- 信息分区、元素类型和优先级。

实现要点：

- 这一层不追求“漂亮”，只追求表达清楚。
- 明确每页最多一个主视觉焦点。
- 每个页面都要指定布局类型：对比、流程、时间线、矩阵、数据卡、Bento Grid、案例拆解等。
- 避免把完整正文直接塞进设计模型，先压缩成适合幻灯片展示的表达。

### 5.5 视觉设计 Agent

输入：

- PagePlan。
- 页面文案。
- 风格约束。
- 可用素材。

输出：

- SVG 或 HTML 设计稿。
- 预览图。
- 设计说明元数据。

实现要点：

- 固定画布为 16:9，例如 1280 x 720。
- 所有元素必须有明确坐标和尺寸。
- 文本必须有字号、行高、最大宽度和换行策略。
- 卡片间距建议不小于 20px。
- 重要内容使用更大的卡片或更高视觉权重。
- 每页生成后必须跑校验，不合格则自动回修。

## 6. SVG 路线的技术细节

### 6.1 为什么适合 PPT Agent

SVG 的优势：

- 矢量清晰。
- 单页可以作为一个完整设计资产。
- 能被 Office 导入。
- 文本、形状、路径、图标理论上可编辑。
- 代码形态适合 LLM 生成与修改。

SVG 的风险：

- Office 对部分 SVG 特性的支持不完整。
- 文本自动换行需要自己处理。
- 外链图片、字体、滤镜、渐变、遮罩可能导入失败或变形。
- 复杂 SVG 可能导致 PPT 卡顿。
- 生成质量很依赖模型的代码能力和校验回路。

### 6.2 SVG 生成约束

建议给模型的硬约束：

```text
画布：viewBox="0 0 1280 720"
安全边距：左右至少 48px，上下至少 40px
文本：禁止超出卡片边界；标题不超过 2 行；正文不超过 4 行
布局：优先使用卡片式网格；卡片间距至少 20px
字体：使用系统字体栈，避免依赖特殊字体
图片：优先使用内嵌 base64 或经过代理的稳定资源
兼容：避免复杂 filter、foreignObject、外链 CSS
输出：只输出完整 SVG，不混入解释文字
```

### 6.3 SVG 校验器

建议实现一个自动校验器，至少检查：

- XML 是否可解析。
- viewBox 是否正确。
- 是否包含不兼容标签，比如 `foreignObject`。
- 文本元素是否超出估算边界。
- 是否存在外链资源。
- 是否有过小字号。
- 颜色对比度是否过低。
- 是否有空白页或元素数量异常。

可选增强：

- 使用 headless browser 渲染 SVG 成 PNG。
- 用视觉检测判断是否有元素重叠。
- 用 OCR 检查文字是否被截断。
- 导入 Office 或 LibreOffice 做兼容性回归测试。

## 7. HTML 路线与 PPTX 路线

### 7.1 HTML 作为 MVP 更快

如果你先做个人版或内部验证，建议先用 HTML：

- CSS 布局比 SVG 更好写。
- 文本换行天然可靠。
- 预览和调试简单。
- 可以用 Playwright 截图生成页面图片。

缺点是导入 PPT 后可编辑性较弱，通常需要转图片，或者再做 HTML -> PPTX 转换。

### 7.2 PPTX 原生对象作为最终商业路线

如果你希望生成真正可编辑的 PPT，最终可以考虑直接生成 PPTX 原生对象：

- 文本框、形状、图片、图表都作为 PPT 对象写入。
- 可用 PPTXGenJS 或 python-pptx。
- 需要自己实现布局引擎和视觉系统。

推荐演进路线：

```text
阶段 1：HTML / SVG 快速验证生成质量
阶段 2：SVG 导入 PPT，解决兼容性和编辑性
阶段 3：关键页面类型转 PPTX 原生对象
阶段 4：模板、品牌规范和企业资产库深度集成
```

## 8. 布局系统设计

### 8.1 默认布局类型

建议内置以下页面布局：

- Cover：封面。
- TOC：目录。
- Section Divider：章节页。
- Bento Grid：多信息卡片页。
- Hero + Cards：一个大观点加多个支撑点。
- Comparison：左右对比或多列对比。
- Timeline：时间线。
- Process：流程。
- Matrix：二维矩阵。
- Dashboard：指标看板。
- Case Study：案例拆解。
- Quote / Statement：金句页。
- Closing：总结页。

### 8.2 Bento Grid 布局策略

根据内容数量选择布局：

- 1 个核心点：单焦点大卡片。
- 2 个并列内容：左右均分或 2/3 + 1/3。
- 3 个并列内容：三列卡片。
- 4 个内容：2 x 2 网格。
- 5 个内容：一个大卡片 + 四个小卡片。
- 6 个以上：分组后再展示，避免一页过载。

不要让模型完全自由放置。更稳的做法是：

1. Agent 判断内容结构。
2. 选择布局模板。
3. 布局引擎给出坐标。
4. 设计模型在坐标内做视觉表达。

## 9. Prompt 设计建议

### 9.1 需求澄清 Prompt

```text
你是资深 PPT 顾问。请基于用户主题和初步资料，判断还缺哪些关键信息。
只提出会显著影响 PPT 结构和表达策略的问题。
问题数量控制在 3 到 6 个。
每个问题给出一个默认选项，方便用户快速确认。
输出 JSON：questions、assumptions、next_step。
```

### 9.2 大纲 Prompt

```text
你是 PPT 结构架构师。请基于主题、受众、目标、页数和调研摘要，设计一份结构严密的 PPT 大纲。
要求：
1. 每页必须有 core_message。
2. 章节之间要有递进关系。
3. 内容必须引用调研摘要中的事实，不要凭空编造。
4. 输出严格 JSON，不要输出解释。
```

### 9.3 页面策划 Prompt

```text
你是 PPT 策划师。请把单页内容转成低保真页面策划稿。
要求：
1. 明确页面主旨。
2. 拆分信息区块。
3. 为每个区块指定元素类型、视觉权重和建议位置。
4. 选择最适合的布局类型。
5. 输出 PagePlan JSON。
```

### 9.4 SVG 设计 Prompt

```text
你是信息架构和 SVG 设计专家。请根据 PagePlan 生成一页 1280x720 的 SVG 幻灯片。
要求：
1. 使用 Bento Grid 或指定布局。
2. 所有元素必须在安全边距内。
3. 文本不得溢出容器。
4. 保持专业、简洁、高级感。
5. 避免 Office 兼容性差的 SVG 特性。
6. 只输出 SVG 代码。
```

## 10. 质量控制闭环

高质量 PPT Agent 的关键不是一次生成，而是自动评审和回修。

建议每页生成后走以下检查：

```text
结构检查
  -> 是否符合本页 core_message
  -> 是否与章节逻辑一致

事实检查
  -> 是否有资料来源
  -> 是否出现无依据数字

文案检查
  -> 是否过长
  -> 是否像 PPT 语言
  -> 是否标题和正文重复

视觉检查
  -> 是否有主次层级
  -> 是否拥挤
  -> 是否留白不足
  -> 是否对比度不足

技术检查
  -> SVG 是否可解析
  -> 是否可渲染
  -> 是否可导入 PPT
```

每项检查给出结构化结果：

```json
{
  "passed": false,
  "issues": [
    {
      "type": "text_overflow",
      "severity": "high",
      "location": "block_2",
      "suggestion": "将正文压缩到 2 行，或改成 3 个短 bullet"
    }
  ]
}
```

## 11. MVP 实现路线

### 11.1 第一版：可跑通闭环

目标：输入主题后，生成 8 到 12 页可预览的 SVG 或 HTML。

功能范围：

- 主题输入。
- 需求澄清。
- 搜索资料。
- 生成大纲。
- 便利贴编辑。
- 每页生成策划稿。
- 每页生成 SVG。
- 页面预览。
- 下载 SVG / PPTX。

暂不做：

- 复杂模板继承。
- 企业品牌资产库。
- 多人协作。
- 全自动事实核查。
- PPT 原生对象深度编辑。

### 11.2 第二版：质量提升

- 增加页面级检索。
- 增加自动评审和回修。
- 增加更多布局类型。
- 增加品牌色和字体约束。
- 增加历史版本和局部重生成。
- 支持用户在策划稿阶段精修内容。

### 11.3 第三版：商业化能力

- 支持上传企业模板。
- 自动解析模板配色、字体、版式。
- 支持企业图标库、图片库、案例库。
- 支持 PPTX 原生对象生成。
- 支持团队工作流和审批。
- 支持基于行业知识库的专属生成。

## 12. 关键工程难点

### 12.1 内容难点

- 用户输入太少，Agent 需要主动澄清。
- 搜索结果可能过时或不可靠。
- 大纲可能逻辑松散。
- 页面文案可能太像文章，不像 PPT。

解决方向：

- 需求澄清前置。
- 检索资料结构化。
- 每页绑定核心观点和证据。
- 让文案 Agent 专门做 PPT 化压缩。

### 12.2 设计难点

- 模型容易堆砌元素。
- 页面主次不清。
- 字太多。
- 风格不稳定。

解决方向：

- 先出策划稿，再出设计稿。
- 默认使用卡片布局。
- 控制每页信息密度。
- 用风格 token 统一字体、颜色、圆角、阴影、图标风格。

### 12.3 导出难点

- SVG 导入 PPT 后可能丢失样式。
- HTML 转 PPT 后可编辑性差。
- PPTX 原生生成工程量大。

解决方向：

- MVP 用 SVG / HTML 快速验证。
- 对 SVG 做兼容性白名单。
- 高价值页面类型逐步实现 PPTX 原生组件。

## 13. 自研时的推荐状态机

```text
created
  -> requirement_collecting
  -> researching
  -> outline_generated
  -> outline_reviewed
  -> page_planning
  -> page_plan_reviewed
  -> designing
  -> validating
  -> exported
```

每个状态都要可暂停、可回滚、可局部重跑。例如用户改了第 5 页标题，不应该整套 PPT 全部重做，而是只重跑第 5 页的资料、策划稿、设计稿，并检查相关上下文。

## 14. 给你的落地建议

如果你现在要做自己的 PPT Agent，我建议按这个优先级实现：

1. 先做“结构质量”：需求澄清、大纲、页面卡片。
2. 再做“页面策划”：把每页变成可解释的布局计划。
3. 再做“视觉生成”：从 PagePlan 生成 SVG 或 HTML。
4. 最后做“导出编辑”：SVG 导入 PPT，或逐步转 PPTX 原生对象。

最小核心不是“生成 PPT 文件”，而是建立一套稳定的中间表示：

```text
Topic -> Requirement -> Research -> Outline -> SlideCard -> PagePlan -> DesignArtifact -> Export
```

只要中间表示设计好，后续无论你换模型、换搜索接口、换渲染方式，都不会推倒重来。

## 15. 一句话总结

这套 PPT Agent 的真正价值在于：用 Agent 复刻专业 PPT 团队的分工，把“做 PPT”拆成需求、资料、结构、策划、设计、校验、导出的可控链路。SVG 只是最终表达层，核心壁垒是前面的内容理解、页面策划和质量闭环。
